结论：**D1 集中取数、D2 保留 ODS 视图、D10 新建独立业务域，这三个方向可以保留。现有材料未证明已经发生跨项目破坏，但不足以支持“视图层 100% 完成”或具备真实发送条件。** 优先解决就诊标识、补改与撤销捕获、关联依赖和回执语义。

以下仅依据内联材料；“实测”均指材料所述结果，本轮未读取文件、执行命令或修改文件。

对跨项目冲突的判断如下。

1. **没有发现同名覆盖证据；同 schema 的主要问题是授权与变更治理。**  
   `V_INF_*` 与 `V_EMR_*` 命名区分明确，不必仅为治理清晰立即迁移 schema。应明确视图所有者、工单审批、消费账号、受影响项目和回退责任。独立消费账号及最小授权，比立刻拆 schema 更直接。  
   【出处：方案§三 D2、§四；其他项目摘要 B；GLM B2、D】

2. **ODS 性能风险不能评为“低且可控”，目前只能标记“待验证”。**  
   秒级聚合查询不代表带正文提取、分页、补报时同样稳定；输出行数也不代表底层扫描量。尤其方案提供的是“近 7 天”数量，GLM 将其写成“日批约 2 万行”，缺少换算依据。应验证实际增量 SQL 的执行计划、耗时和并发，以及与三甲月批重叠时的表现。三甲“删当月”发生在目标端，不能直接推导 ODS 的删除负载。  
   【出处：方案§二2、§四；其他项目摘要 B；GLM B1】

3. **与 drug_trace 最需要隔离的是生产运行资源和配置。**  
   若复用同一部署，应隔离连接池、任务队列、并发额度、重试、任务锁及域配置；新增迁移和发布不得拖垮现有生产任务。06:00—08:30 是现有维护约束，仅避开 07:30 不充分。drug_trace 的发送授权也不能延伸为传染病发送授权。  
   材料还有一处口径差异：方案写 `BLYB_RO`，后附事实摘要写 `BLYB_DRUGTRACE`、PHARMACY 两视图，复用配置前必须统一。  
   【出处：方案§二6、§四；其他项目摘要 A、E；工作区约定“真实接入单独授权”】

4. **“院内直连”是设计路径，尚不是可达性证据。**  
   GLM 据此断言“网络路径无冲突”过早。还需确认实际 worker／容器到前置机的路由、ACL及目标端口。新通道应独立配置目的端，不能放宽药品通道的全局转发规则。接口无鉴权且传输病历正文，调用方限制和网络访问范围必须明确。  
   【出处：方案§二1、§二4、§三 D10；其他项目摘要 A；GLM B3】

5. **CDA 字典是本项目的运行依赖；死亡表零命中只是待查线索。**  
   41,978 条映射不能证明映射唯一、有效或版本适用。需明确院标、国标版本、有效期及一对多处理，禁止随意取第一条；字典变化也可能改变已上报文书内容。死亡表零命中可能来自关联键、机构、时间范围或数据生成条件，不能直接认定互联互通停更。  
   【出处：方案§二3、§三 D8；其他项目摘要 C；GLM B5】

6. **医保电子病历、病理项目只能列为“冲突尚未排查”。**  
   完成度、部署位置和调度均未知，不能认定无冲突；病理不走 ODS，也不能排除共用 worker、数据库、路由或账号的冲突。  
   【出处：方案§四；其他项目摘要 D】

架构方面，以下问题应优先处理。

7. **【真实发送前阻断】患者标识与就诊标识必须分开。**  
   PMI.INP_NO 跨次住院不变，已知不能单独区分就诊；文书 ID 含 VISIT_ID，不能自动弥补 `serial_number` 的关联语义。  
   建议内部明确患者键、就诊键和文书键：就诊键至少能区分机构、患者及住院次数；所有五类文书使用一致映射，保留原始前导零。外部 `serial_number` 则按接收方规则确定。**我同意 GLM 指出硬伤，但不支持未经确认直接拼接“病案号-VISIT_ID”作为外部口径，更不接受“维持现状赌前置机”的选项。**  
   【出处：方案§三 D3；GLM C1；工作区约定“患者/就诊分离、前导零”】

8. **【真实发送前阻断】五类文书范围，不等于排除必要基础关联。**  
   所附用户原话明确排除了传报卡，但未看到明确排除四张伴生表的原话，不能据此认定 D4 已获逐项拍板。  
   同时，GLM 判断“不推必然拒收”也证据不足：基础数据可能已由其他系统维护。应逐项确认必需关系、已有数据、标识一致性及同步责任，再决定本项目需要补什么。特别是 GLM 建议补三张表，却没有解决其自己强调的 `emr_activity_info` 就诊关联。  
   【出处：方案§一、§三 D4；GLM A、C2】

9. **首页“已出院”不能直接认定为“已定稿”。**  
   `DISCHARGE_DATE 非空`只证明出院，不能证明首页已保存、签署、审核或不再补改。若接收规范确为“保存后当天”，当前筛选存在触发口径缺口。应区分文书保存／定稿时间、临床出院时间和最后修改时间。  
   我也不接受 GLM 把“入院 24 小时内已有初页”直接当成本项目事实；材料没有给出相应来源。  
   【出处：方案§三 D5；GLM C3】

10. **【真实发送前阻断】增量不能只靠一个水位字段。**  
    OPERATION_TIME 只有在覆盖全部相关变化时才可靠：首页诊断、正文、检查项目、关联信息及映射规则的变化，都可能改变输出。需要明确每类数据的变更来源，并处理同时间戳、迟到数据和部分发送失败；扫描进度与逐条投递状态应分开保存。  
    GLM 提议的“诊断修改时间与出院时间取大”只能覆盖部分来源；“每天重推 T-1”也会遗漏更早文书的补改。应有增量、重叠回扫和周期核对的组合。  
    【出处：方案§三 D5、D6；GLM C6】

11. **撤销和删除必须单独设计，不能归入普通更新。**  
    报告作废后可能从 `JOIN EXAM_REPORT` 的结果中消失，普通轮询将看不到它；检查项目删除也一样。需要可靠的作废标记、删除事件或对账机制。  
    另一个证据缺口是：方案只给出“按 ID 更新”，未提供删除接口。GLM 所说“规范支持删除”应补原文和接口定义，不能先按已支持实现。  
    【出处：方案§二4、§三 D6；GLM C6；工作区约定“未知能力显式报错”】

12. **六视图需要验证关联粒度，不能只验证 VALID 和非空率。**  
    检查与 PAT_VISIT 的连接必须落到同次就诊；仅按患者关联，可能把门诊检查归入住院或关联到多次住院。嘉和文书、诊断、CDA 记录也应检查一对多放大。  
    检查主表 6,081、项目 5,947，需要解释无项目报告是否允许，并核对孤儿项、重复项和晚到项；数量本身不能证明异常，也不能证明正确。还需明确主／子记录的发送顺序及重试方式，避免永久缺项。  
    【出处：方案§二2、§二5、§三 D6；GLM A】

13. **【真实发送前阻断】死亡字段的描述存在内部矛盾。**  
    D8 同时写“兜底出院主诊断”和“死亡诊断恒空”，必须先区分死亡诊断、死亡原因及其实际映射。出院主诊断不能未经核实直接标作死亡原因；死亡时间也不能随意用出院时间替代。若适用的必填字段确实取不到，应进入质量等待并保留原因。  
    【出处：方案§三 D8；GLM C4前相关判断；工作区约定“质量等待、证据门 fail-closed”】

14. **2000 字截断是当前提取方式的限制，不应直接接受为数据完整性标准。**  
    SQL VARCHAR2 的字节限制，不等于 Oracle 驱动不能读取 CLOB，也不等于接口只允许 2000 字。“建议填”说明必填级别，不能证明截断符合字段语义。  
    不要求本期完成结构化拆分，但应评估保留完整正文的提取方式。若暂时截断，至少保留源长度、截断标记和规则版本；正文已经截断后，仅看输出无法准确统计截断率。  
    【出处：方案§二5、§三 D7；GLM C4、D】

15. **机构码和映射规则应集中配置并固定 revision。**  
    前置机信息到位后逐张替换六个常量，容易造成版本不一致。应核对院内机构标识与国家分配标识的字段含义，由统一配置或版本化映射控制；占位值必须被真实发送通道拒绝。旧冻结 payload 保留，更正生成新 revision。字典版本也应纳入可追溯范围，不能只固定一个仍会变化的配置引用。  
    【出处：方案§三 D9；其他项目摘要 C、E；工作区约定“冻结包不原地改、配置 revision 固定”】

16. **【真实发送前阻断】可以简化药品流程，但不能删掉通用证据门。**  
    我反对 GLM 把流程简单归结为“发送→回执入库→失败重试”。需要依据接口定义区分：发送结果未知、HTTP 返回、接口受理及业务确认；接口未提供的确认能力应明确标未知。  
    还要处理一个关键顺序问题：**旧版文书失败重试，不能覆盖已发送的新版文书。** 外部文书 ID 应稳定，内部记录版本和冻结 payload，并约束同一文书的发送次序。租户／owner 隔离、质量门、授权门、Mock 标识和 dry-run 零真实副作用均应保留。  
    【出处：方案§二4、§三 D10；GLM C5；其他项目摘要 E】

17. **T+0 必须验证整条链路，不能由“ODS 延迟满足”直接推出。**  
    还包括提取等待、排队、质量等待、重试及前置机处理。一天只扫一次，可能遗漏扫描后新增的当天文书。应明确 T+0 的计时起点、截止口径和成功状态，并分别记录源事件、ODS 可见、提取、发送及回执时间。  
    【出处：方案§一用户答复、§二1；GLM B1、C6】

对 GLM 的总体评价是：**支持其指出 serial_number、漏补改、治理责任及 MOCK 可先行；反对把假设写成确定结论，以及用流程简化替代必要门禁。**

尤其需要修正三项表述：

- **“视图层 100%”缺少验收依据。** 已部署、VALID、查询有数据，只能证明部分技术检查完成，尚未证明就诊关联、唯一性、完整性及接收语义正确。【出处：GLM A；方案§二2、§三 D3—D8】
- **“推送器未开发是外部阻断”不成立。** 缺前置机信息阻断真实联调，但未阻断离线契约、质量校验、冻结 payload、增量和 MOCK。GLM D 中自己的流程建议也支持这一点。【出处：GLM A、D；方案§二6】
- **“院内只读所以低风险”“以后任何人都能读”均不准确。** 前者忽略病历正文的访问边界，后者需要实际授权链才能成立。应列出谁获得了哪些对象权限、谁能消费这些视图，再作判断。【出处：GLM B4；方案§二3】

建议下一轮对辩优先补四项证据：**外部就诊键规则、基础表既有数据与必需关系、各类文书补改／撤销机制、回执字段的确切语义。** 这些问题明确后，再固化推送器契约；无需因此重建现有架构。
