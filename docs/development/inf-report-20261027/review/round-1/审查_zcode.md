## B. 冲突自查（对方案 §四逐项）

1. **ODS 8.216 性能冲突：低但真实。** 三甲复审是按月批抽取，本项目 T+0 日批轮询 6 视图；实测视图查询全部秒级聚合通过（FIELD_MAPPING §9-12），日批量 ~2 万行级，冲突可控。真冲突点在**异常日重扫**：若推送器故障积压 3 天，重扫窗口放大与三甲月末批（删当月+插当月，量大）可能同日叠加——建议推送器限速+错峰（避开月末/07:30 drug_trace SLA 窗）。
2. **视图治理边界：存在实质模糊。** V_INF_* 建在 ODS schema 与三甲 V_EMR_* 同域，但本项目属 blyb 栈（信息科线）而 ODS 属数管中心线。当前靠用户本人=DBA 兼任消解，**若未来两线分人，DDL 责任与变更通知无书面约定**。建议：至少在 数据上报/4 README 里把"6 张视图的变更走谁"写死。
3. **与 drug_trace 栈内冲突：方向不同不互斥。** drug_trace 出互联网走 DMZ 白名单（eco.taobao.com 固定上游），传染病前置机是**院内内网直连**，不经 DMZ——网络路径无冲突；但 worker 需新增第二个 Oracle 源（ODS 8.216），凭据/连接池/任务调度与 drug_trace 的 HIS 源并行，运维面+1。
4. **JHEMR 授权治理：已产生既成事实。** 为建视图给 ODS 授了 JHEMR 两表 SELECT（DBA_TAB_PRIVS 实证）。这是数据中心库上首次出现 ODS schema 读嘉和文书的先例——以后任何人都能借 ODS 视图读病历正文。低风险（院内只读）但应在数据资产平台登记此授权，避免变成无主后门。
5. **CDA 死亡表零命中不影响三甲/互联互通**：我们只读不写，无冲突；但说明该共享文档区可能已停更——这对**互联互通上报项目本身**是个预警信号，值得单独告知数管中心（不是本项目的问题，是发现的相邻问题）。

## C. 架构完善建议（我方立场，欢迎攻击）

1. **serial_number 语义隐患（方案 D3）：我方认为这是当前设计最大的硬伤。** PMI.INP_NO 是病案号，同一患者多次住院会重复。规范值域注释"诊疗活动为住院期间时，就诊流水号为住院号"且质控要求各业务表通过就诊流水号与诊疗活动表有效关联——若前置机把 serial_number 当唯一就诊键，两次住院的首页/病程/检查会串档。候选修法：①serial_number = PMI.INP_NO || '-' || VISIT_ID（全院口径变更需与病案科确认"住院号"官方定义）；②维持病案号，赌前置机只用 ID+patient_id 关联。我倾向①，但**这是口径决策，需用户/病案科拍板，AI 不应单方定**。
2. **伴生表风险被低估（D4）：联调首日就会撞墙的概率高。** 规范校验规则明确"必填不填将无法通过前置软件校验，数据无法存储"，且 dept_code/operator_id 值域锚在 base_dept/base_user。不推 base 表，5 类文书里 org/dept/operator 全部必填字段拿什么通过校验？我判断：**D4 的"联调若拒收再补"过于乐观——不是若，是必然**，建议把 base_user/base_dept/emr_patient_info 提为期前必做（工作量小：三张表都是薄表）。
3. **在院患者首页不推（D5）：与规范触发时机不符但有理。** 规范 T+0 触发="病案首页保存后当天"，在院期间首页也会保存（入院 24h 内完成初页）。当前只在出院后推，前置机侧"当日病案首页完整率"质控可能扣分。建议二期补"在院初页"推送（需嘉和 first_page 表增量），本期接受。
4. **正文 2000 字截断（D7）：可接受但应在推送器侧记录截断率**，若前置机侧有"内容完整"类分析需求（哨点监测要看病程文本），截断会伤分析质量——二期 CLOB 直读时一并解决。
5. **推送器架构：复用 drug_trace 骨架合理，但要砍掉不适用的部分。** drug_trace 的证据门/确认门为药品上报设计（发码→确认→对账三段），传染病是单向推送+回执，简化为"发送→回执入库→失败重试"即可，不要照搬三段门禁增加操作负担。MOCK 通道先行不变。
6. **增量水位已内建**（各视图 OPERATION_TIME），推送器只需记录上次水位；但**修改/删除场景**（医生补改病历、作废检查报告）规范支持按 ID 更新/删除推送——当前方案没有变更捕获机制（嘉和 last_modify 已进视图，首页改诊断后出院时间不变→水位不动→漏推）。建议：首页视图水位改用"诊断表最近变更时间或出院时间取大"，或推送器每日重推 T-1 全量（幂等更新）。**这是真实缺陷，需修。**
