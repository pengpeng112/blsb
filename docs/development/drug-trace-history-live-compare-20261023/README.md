补查这些候选码，现能找到的1296条视图记录全是14位数字前缀的另一类明细（1287条正常门诊、9条UNKNOWN）。这支持“存在另一种历史标识/来源分支”的判断，**仍不足以直接认定它就是住院、拆零或某一张具体源表**。

需要确认的是：这5077条旧明细对应的原扫码记录是否仍在，原PRESC_DETAILID是否确实与文件完全一致，三项主单关联是否命中，以及该业务应走哪个主单来源。
当前专用账号只允许两视图；本轮没有转用广权限账号绕过限制，因此无法从生产内连接视图看到被JOIN排除的原始记录，也不能排除原记录已被物理删除/变更或历史导出另有映射。

## 4. 重复码确实存在，现程序会怎样处理

31组历史同明细同码各2次出现，在视图中都对应2条有效、不同ID的扫码记录。
已取真实整单快照，在本机直接调用**现有**`quality.evaluate_revision`纯判定函数，无数据库写入：

| 样本 | 整单码行数 | 结果 |
|---|---:|---|
| 常规历史单样本 | 1 | VALID，仅包装层级未确认告警 |
| 重复出现样本所在整单 | 12 | **INVALID，QD-DUP-CODE阻断** |

因此“历史行/次数已对上”不等于“整单可发送”。31组也不等于31张不同主单，不能直接按组数统计失败主单数。
需查拆零、重扫、更正等真实原因；保留来源记录和次数，不直接DISTINCT、MAX或放松重复码规则。
