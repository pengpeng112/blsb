### 步骤 2：在平台 `blyb_platform` 实现一等公民企业微信通知通道（`wecom_relay` + `wecom_robot`）

打开 `implementation/plugins/alerting/channels.py`、`evaluator.py`、`rules.py`、`redact.py`、`seeds.py` 与 `apps/core_api/ops_routes.py`：

1. **扩展通道类型与严格安全校验（`channels.py`）**：
   - 支持通道类型：`("file", "wecom_relay", "wecom_robot", "smtp", "webhook")`（若 `NotificationChannel.type` 列长度不足，编写幂等编号迁移 `023` 确认兼容 SQLite/PG；`String(16)` 本身已可容纳 `wecom_relay` 11 字符与 `wecom_robot` 11 字符，但迁移 `023` 可一并加上通道扩展校验与后续观测表）。
   - **`wecom_relay` 允许字段白名单**：`{"url_env", "secret_env", "source_id", "category", "quiet_hours", "rate_limit_per_min"}`：
     - `url_env` 与 `secret_env` 必填且必须匹配 `^[A-Z][A-Z0-9_]{2,63}$`（严禁任何明文 URL 或明文 secret 入库！`_iter_secret_paths` 继续拦截任何非 `*_env` 的敏感键）；
     - `source_id` 必填（匹配 `^[a-z0-9][a-z0-9_-]{2,63}$`，如 `blyb-platform-alerting`）；
     - 协议实现与院内 `wechat-relay` v2 完全一致：`POST {url}`，先序列化紧凑 UTF-8 JSON 字节 `raw`，再用 `HMAC-SHA256(secret, f"{source_id}.{ts}.".encode() + raw)` 生成小写 hex `X-Signature`，附带 `X-Source-Id` 与 `X-Timestamp`，严禁携带 `receivers` 字段；`200/202` 视为成功，`502` 原字节重试 1 次，`429/503` 短退避重试 1 次。
   - **`wecom_robot` 允许字段白名单**：`{"url_env", "msgtype", "quiet_hours", "rate_limit_per_min"}`（支持企业微信群机器人 `markdown` 与 `text` 卡片格式，且**必须解析响应 JSON 校验 `errcode == 0`**，防止 HTTP 200 但 `errcode: 93000` 被误判为发送成功！）。
   - **双重安全外发门控**：
     - 平台支持随时创建、编辑 `wecom_relay` / `wecom_robot` 通道，并无条件开放 **`dry_run=True`（零出网渲染预览）**：校验环境变量是否已注入、输出脱敏后的请求头摘要与完整渲染后的中文企微卡片标题/正文，写入审计与 `notification_log`（状态 `DRY_RUN_OK`）；
     - 支持 **`probe=True`（网关真达探测，仅管理员且配置了 `BLYB_ALLOW_EXTERNAL_NOTIFY=1` 时可执行）**：对 `wecom_relay` 发送无签名空包校验 `HTTP 401 Missing X-Source-Id`，验证隧道/网络真达而不向任何企微用户推消息！
     - 真实告警外发与 `test` 实发：当环境变量 `BLYB_ALLOW_EXTERNAL_NOTIFY=1` 时放行 `wecom_relay` / `wecom_robot` 启用与发送；未设置该环境变量（默认本地开发/测试环境）时，启用或实发返回清晰中文说明 `当前环境未开启外发开关（BLYB_ALLOW_EXTERNAL_NOTIFY），可使用“预览卡片”验证配置`，确保本地测试 100% 零真实外发副作用！

2. **升级告警评估引擎 `evaluator.py`、`rules.py` 与中文卡片格式化**：
   - **结构化 `AlertEnvelope`**：重构 `redact.py` / `channels.py` 消息组装，彻底淘汰丑陋的 `last_notified_at=... backlog_total=...` 裸键值串，统一生成清晰中文结构：
     - 标题：`【严重/警告/已恢复】{业务中文名} · {规则中文名}`
     - 正文：`所属业务`、`触发规则`、`当前现象`、`首次发现 / 持续时长 / 累计次数`、`处置指引`。
   - **修 `WARN → CRITICAL` 升级不通知 Bug（`evaluator.py:141-165`）**：当已有 `OPEN`/`ACKED` 告警本次评估级别高于原 `ev.severity` 时，立即更新 `ev.severity` 并**无视冷却期立即外发 `【升级·严重】` 通知**！当告警自动恢复（`RESOLVED`）且此前曾外发过通知时，自动发送一条中文 `【已恢复】` 通知（含持续时长）。
   - **新增告警风暴抑制与夜间静默窗**：同一轮评估若单通道待发告警 `> 5` 条，自动合并为 1 条 `【告警聚合】本轮共触发 N 条告警（严重 X / 警告 Y）` 摘要消息；支持通道级 `quiet_hours`（夜间压制 `INFO/WARN` 外发，`CRITICAL` 照常即时外发，本地库与 `file_default` 照常记录）。
   - **修复传染病假告警并新增 3 类实用规则（`rules.py` + `seeds.py`）**：

     - 新增规则类型：`WATERMARK_STALE`（子表最大水位滞后超 N 小时）、`PARENT_WAIT_OVER`（待父受理积压超 N 条）、`WATCHDOG_STALE`（外部守护 `status.json` 超过 N 分钟未刷新或 overall 为 `CRITICAL`）——让平台与 `inf_watchdog` 形成双向交叉守护！
