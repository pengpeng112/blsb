### 步骤 2：重构 `pusher.py` 统一父版本状态解析器（解决 R2 / F04 / F05 + `exam_item` 门禁）

打开 `implementation/deploy/inf_pusher/tables.py` 与 `pusher.py`：

1. **补齐 `tables.py` 主子门禁声明**：
   - 检查全部子表：`exam_item`（`tables.py:170-186`）已有 `"depends_on": "exam"`，补上 `"parent_fk": "exClinicalId"`；确认 `ex_lab_item`（`"depends_on": "ex_lab"`, `"parent_fk": "exLabId"`）与 `order_item`（`"depends_on": "order"`, `"parent_fk": "orderId"` 或现有实际键名，以 `tables.py` 现有定义为准）完整一致。
2. **新增规范化父内容版本摘要函数 `payload_version_digest(payload)`**：
   - 计算除去动态上传时刻（即保留源 `operationTime` 或在替换为 `now(CST)` 之前的规范化业务字段 dict，`json.dumps(..., sort_keys=True, ensure_ascii=False)`）的 `sha256` 前 32 位。
   - `ReceiptLog.mark_sent(table, rid, op_time, digest="")`：向 `sent.jsonl` 写入 `{"id": "table/rid", "opTime": op_time, "digest": digest, "table": table, "ts": now_str()}`（向后兼容无 `digest` 的历史旧行，旧行 `digest=""` 视为 `LEGACY`）。
   - `ReceiptLog.receipt(...)`：成功/失败回执可选携带 `opTime` 与 `digest`（**严禁把患者姓名/证件号等 payload 明文写入回执！**）。
3. **建立统一的 `ParentAcceptanceTracker` 类（供 `main`、单表、`run_reconcile`、`--replay-manifest` 共用，彻底消灭死参数 `parent_accept`）**：
   - 命名空间键固定为 `f"{parent_table}:{parent_id}"`。
   - 数据来源合并两层：
     a. **历史持久层（`sent.jsonl`）**：加载 `parent_table` 历史最后一次成功发送的 `{"op_time": ..., "digest": ...}`（支持跨日有效父复用，满足 `prior_day_accepted_parent_new_child` 与 `order_historical_parent_new_child`！）。
     b. **本进程/本班次实时覆盖层（`session_outcomes`）**：当本班次（含 `main` 或 `run_reconcile`）处理父表某条记录 `parent_id` 时：
        - 若真实发送成功（`mode == "real"` 且 `resp.result is True`）：登记 `session_outcomes[pkey] = {"status": "ACCEPTED", "op_time": op_time, "digest": digest}`；
        - 若幂等跳过（`skipped_same`，即源时间未变且历史已受理）：登记 `session_outcomes[pkey] = {"status": "ACCEPTED_HISTORICAL", "op_time": op_time}`；
        - **关键防绕过（解决 `same_day_old_parent_current_rejected` 与 `reconcile_stale_parent_current_rejected`！）**：若父表记录在本班次发生 **`client-validate` 缺必填、`02/03/04` 平台拒绝、`01/99`/网络重试耗尽失败、或父表自身异常**，立即登记 `session_outcomes[pkey] = {"status": "FAILED_CURRENT", "op_time": op_time}`！
        - 同时扫描当日 `receipts-YYYYMMDD.jsonl`：若针对同一 `parent_table` + `parent_id`，当日最新一条非 mock 回执为 `result == False`（即早先单跑父表刚失败，紧接着单跑子表），同样视为 `FAILED_CURRENT`！
        - `mode == "mock"` 的回执**永不**作为 `real` 模式放行子表的受理证据！
   - 子表门禁判定 `tracker.is_parent_ready(parent_tbl, pval)`：
     - 若 `pval` 为空 → `False`（原因 `父键为空`）；
     - 若 `session_outcomes.get(pkey)` 状态为 `FAILED_CURRENT` → **必须返回 `False`**（原因 `当前父版本未受理`，**绝不允许被 `sent.jsonl` 旧成功记录覆盖绕过！**）；
     - 若 `session_outcomes.get(pkey)` 为 `ACCEPTED` / `ACCEPTED_HISTORICAL` → `True`；
     - 若本班未扫到该父（如跨日父未变更落在本班父窗口外，或单跑子表），且当日最新回执非失败、且 `sent.jsonl` 存在该 `parent_tbl:pval` 真实记录 → `True`。

### 步骤 3：实现持久化等待队列 `PendingWaitStore`、原子写与流式游标取数（解决 R3 / F06 + OOM 防护）

1. **所有本地状态文件改为原子写入 `atomic_write_json(path, data)`**：
   - `Watermark.advance()`、`last-run-*.json`、`reconcile-*.json`、`pending-wait.json`、`manifest-state-*.json` 一律先写同目录临时文件 `f"{path}.tmp.{os.getpid()}"` + `flush()` + `os.fsync()` 再 `os.replace()`，彻底杜绝进程被杀导致 `watermark.json` 变空文件引发 180 天全量重扫事故！
2. **新建 `PendingWaitStore`（持久化文件 `<workdir>/pending-wait.json`）**：
   - 结构：`{"version": 1, "items": {"<table>/<id>": {"table": name, "id": rid, "parent_table": parent_tbl, "parent_id": pval, "first_seen_at": ..., "last_checked_at": ..., "op_time": op_time, "attempts": n, "reason": "parent-wait"}}}`（**只存表名/记录ID/父ID/源时间/原因，绝不存患者敏感字段！**）。
   - **执行顺序（解决 `waiting_row_lost_outside_overlap`！）**：
     - 在 `run_table()`（`mode == "real"` 且非受限 `replay_manifest` 模式）开始扫增量窗口**之前**，先读取 `PendingWaitStore.list_for_table(name)` 中已登记的待办 `id` 列表；
     - 若该表存在不在当前增量窗口结果集中的待办 `id`，通过参数化受限 ID 查询 `fetch_rows_by_ids(..., view, id_col, pending_ids)`（每批 ≤500 个 ID）从源视图定向捞回最新行快照！
     - 若捞回后父表已就绪且推送成功 → 从 `PendingWaitStore` 移除该项（`recovered_from_wait += 1`）并记入 `sent`；
     - 若源视图中该行已不存在（如源端作废删除）→ 标记并移入 `expired` 统计，不死锁；
     - 若本次扫描或待办重试中仍因 `parent-wait` 被拦截 → 写入/更新 `PendingWaitStore`（先持久化到 `pending-wait.json`，这样即使后续较新记录推进了 `watermark.json`，该等待项也 100% 留在 `pending-wait.json` 中跨重启、跨 `overlap_days` 自动恢复，永不丢项！）。
3. **补齐 `run_reconcile` 完整统计恒等式**：
   - `reconcile-<D>.json` 中每张表必须输出：`{"window_rows": ..., "repushed": s["sent"], "recovered_wait": s.get("recovered_from_wait", 0), "parent_wait": s["parent_wait"], "skipped_invalid": s["skipped_invalid"], "failed": s["failed"]}`，顶层汇总新增 `total_parent_wait` 与 `total_skipped_invalid`；当 `total_parent_wait > 0` 时写入 `ALERT-<D>` 一行 `RECONCILE-PARENT-WAIT table=... count=...`，不再用 `total_failed=0` 掩盖未完成子项！
4. **`fetch_rows` 流式分批改造（防 132 万行 OOM）**：
   - 将 `fetch_rows()` 中 `cur.fetchall()` 升级为基于 `cur.arraysize = 2000` + `while True: batch = cur.fetchmany(2000)` 的生成器或分批迭代（保持对现有 `selftest.py` mock 打桩 `fetch_rows` 返回 `list[dict]` 的 100% 向后兼容！）。

### 步骤 4：严格重放清单 `manifest` 预检、定向取数与持久进度（解决 R4 / F07）

重构 `pusher.py` 中 `--replay-manifest` 处理逻辑（必须在进入任何表循环或 `reconcile` 之前执行 `validate_and_load_manifest()`）：

1. **参数组合前置拦截**：

2. **严格 Manifest Schema 校验（解决 `manifest_expired_wrong_target_bad_digest`）**：
   - 必填与校验项：
     - `manifest_id`（非空字符串，用于持久化进度文件 `manifest-state-<manifest_id>.json`）；
     - `table`（必须与 `--table` 完全一致，且不允许 `--table all`）；
     - `target`（若提供或默认要求为 `"inf_cdc_frontend"` / `"<frontend-host>"`，不匹配立即拒绝！）；
     - `source_instance`（若与 `cfg.get("source_instance")` 均存在且不一致，立即拒绝！）；
     - `expires_at`（必填或存在时解析时间：若当前时间 `> expires_at`，立即拒绝 `manifest expired`！）；
     - `max_count`（正整数上限，默认 ≤5000；若 `len(ids/items) == 0` 或 `> max_count` 或存在重复 ID，立即拒绝！）；
     - 支持 `items: [{"id": "...", "expected_source_time": "...", "expected_digest": "..."}]` 及兼容简写 `ids: [...]`（若 `items` 或顶层给了 `expected_source_time` / `expected_digest`，必须在发送前逐行与源视图取回的行核对源时间与规范化摘要——不一致立即标为 `VERSION_DRIFT` 拒绝发送该行并最终非零退出，**不再依赖命令行是否传了 `--since`！**）。
3. **按 ID 定向取数 + 缺失明确报错 + 持久断点续跑（解决 `manifest_missing_target_not_reported` 与 `same_manifest_applied_twice`）**：

   - 在 `<workdir>/manifest-state-<manifest_id>.json` 持久化每个 `id` 的执行状态（`PENDING` / `SUCCEEDED` / `FAILED` + 受理时间与摘要）：**同一个 `manifest` 第二次运行 `--apply` 时，已 `SUCCEEDED` 的记录直接跳过（0 次重复 HTTP 请求！），仅续跑上次 `FAILED` 或 `PENDING` 的未完成项**！即使 `force=True` 也只绕过旧 `sent.jsonl`，**绝不绕过同一 `manifest_id` 自身的已完成账和父表受理门禁**！
