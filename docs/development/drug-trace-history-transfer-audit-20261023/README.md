## 2. 原计划需要改进的地方

### A. 旧探针没有足够的性能依据

原`probe_code.sql`只按`source_line_id IN(3个旧单号)`筛选。视图该字段来自T.PRESC_DETAILID，而[2026-10-19源端索引快照](../his-live-20261019/evidence/03-indexes.json)只显示RECORD_ID、T_TRACE_CODE、TRACE_BILLNO三个索引，未显示PRESC_DETAILID索引。
这不证明当前库一定没有新增索引，也不等于已看过当次执行计划；但足以说明“3个键＋ROWNUM101”不能独立保证低开销。行数上限限制返回，不保证底层扫描量小。

已新建[probe_by_code_r1.sql](probe_by_code_r1.sql)，对同三条历史样本同时约束**原追溯码＋明细号**。trace_code直接对应有索引证据的T_TRACE_CODE；保留101行、30秒及10分钟初始预算。绑定值不写共享文件。
原计划和SQL作为历史证据保留，未原地改成另一版本，也没有建索引或修改视图。

### B. 相同范围还没有落实，不能直接做双向全量结论

按用户此前提供的历史SQL，历史时间候选为扫码CREATE_TIME，单号候选为PRESC_DETAILID；文件是否完整沿用这一映射仍需样本确认，不能仅由同名三列认证。原SQL使用BETWEEN，包含2026-10-12 00:00:00这个上端点；改用左闭右开区间时必须记录边界调整，不能无说明认定两者相同。实际文件最大时间是2026-10-11 23:52:04。
现主单用处方日期/号/药房复合身份，bill_time是发药时间；码视图updated_at是MODIFY_TIME，**都不是历史SQL的CREATE_TIME**。

- 不能拿历史单号直接和source_bill_id逐字比较；先核实它与source_line_id的实际映射。
- 日期前缀只是字符串观察，5077行解析不符合原模式，另有前缀比文件时间早196天；不能把前缀未经证实就当发药日期。
- 仅按现视图bill_time限定7月23日—10月11日，可能漏掉历史窗口内扫码但更早发药的记录；这样的查询无行不能判HIS没记录。
- 单凭目前两视图，无法严格复现历史CREATE_TIME范围，因此不能把发药范围内“视图有、历史无”一律判人工漏报；若只查历史已知键，也不能反向证明没有人工漏掉的整张单。

如要求历史全量双向审计，须先确认经授权的CREATE_TIME/IN_OUT_TYPE等来源审核字段和同范围提取通道；可由DBA提供另一个审计视图revision。不得因此擅自扩权、改r10或直读原业务表。

### C. 视图可见、当前可发送、历史平台成功是三件事

当前码视图仍保留UNKNOWN业务和删除标志，由程序质量规则再决定是否可以上传；旧历史SQL只限制OUT和非空明细号。
某条历史记录能匹配视图，却可能因当前已删除/退费/非本期正常门诊业务而不再符合自动发送范围。这属于需要解释的状态/时点差异，不等于视图错误或应该补报。

文件只有单号、单据时间、码，没有药房/平台成功终态/原始记录ID，不能独立认证489613行均获平台成功；原文件的“单号＋时间＋码”重复0，也不能代替码级平台对账。
必须保留出现次数与原文件行号；同码跨单、同单同码不同时间都先解释业务，不先DISTINCT或先判错报。
