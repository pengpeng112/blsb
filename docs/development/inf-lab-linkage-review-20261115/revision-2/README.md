### F02 · 高：把执行科室当作操作人员

- 当前线上和本地13号将`PERFORMED_BY`放入operatorId兜底，注释称其为检验师。
- 对交接所指6单，ODS聚合实测：6单TRANSCRIPTIONIST为空；PERFORMED_BY命中DEPT_DICT为6、命中STAFF_DICT.EMP_NO为0。
- 因而“operatorId非空”掩盖了语义错误，不能把科室码当作员工号。这6单“缺必填”不应通过编造操作人员解除。

修订：撤除该错误兜底，核实真实检验/审核/申请人员字段与员工字典映射。只有接口允许且人员身份真实、角色语义成立时才使用；无法确定保持质量等待。对已受理的错误operatorId建立有界更正清单，不删除历史回执。

### F03 · 高：H/L仍被映射为耐药，补传前语义修复未落实

- 线上14号仍将一般H/L转为国标12/10（高度/低度耐药），并保留MAX(CLINIC_NO)归属。
- 本例当前38条中，33条标准码空、3条为12、2条为10；与源H 3条/L 2条相符。
- 38条已受理并不证明这5条的实际payload内容；但当前映射错误已经确认，需读前置机这5条实际字段，若相同则定向更正。

修订：按定量/定性/药敏项目语境区分，保留真实值、源异常标志及参考范围；一般定量H/L不转耐药。正/负、药敏的合法映射分开验收，不简单改成另一组“正常/异常”码。

### F04 · 高：父受理门禁可被旧成功或其他表同ID绕过

冻结代码 `pusher.py` 124行起accepted_ids扫描整个当日文件，不是注释所称“本进程/本班次”。571—572行同时写入带表名键和裸ID，359行实际只查裸ID；未核对父内容摘要/revision/来源上下文。

本轮真实调用main/reconcile的隔离复现：

| 场景 | 观察结果 |
|---|---|
| 当日有旧父成功，新版父本次04失败 | 仍调用子HTTP |
| 死亡表记录ID恰与所需检验父ID相同，检验父04失败 | 仍调用子HTTP |
| reconcile有历史父sent，新版父本次04失败 | 仍调用子HTTP |

修订：父证据必须使用`来源/租户/目标/父表/父ID/父内容版本`完整命名空间；统一获取父当前快照与受理状态。当前版本失败/未知时不能被旧成功覆盖。禁止仅把parent_accept空字典改成None来修跨日问题，否则会进一步放宽到无版本历史账。

### F05 · 中高：跨日有效历史父反而导致新子项被卡，且影响医嘱

- main始终传`parent_accept={}`，run_table只有参数为None才读历史sent；父被skipped_same后不产生新回执。
- 旧父前一天已受理、本次内容未变、新子项到达时，main缺少该父当日回执，子项parent_wait，无法按要求复用有效父。
- tables.py还给order_item新增parent_fk，超出原“先修检验、不改其他12表”的边界。同样跨日医嘱父/新条目场景已复现被卡。

修订：统一普通/对账/单子表入口的父状态解析器，支持同一版本已受理父跨日复用。旧账无digest标LEGACY/UNKNOWN，只针对本次需要的父补查/受限重放，不全表重发；新增医嘱门禁须单独通过兼容验收。

### F06 · 高：等待项没有独立持久恢复，水位越过后仍会漏项

- parent_wait仅写普通回执然后continue，没有独立重试队列。
- 后面另一条成功会继续推进同表最大水位，等父项恢复时旧子项可能已经落在overlap之外。
- 实测：旧子项等待1条，较新子项成功将水位推至11-15；重启后旧子项的父已可用，但旧行不再进入采集窗，仍未发送。
- reconcile汇总只保留repushed/failed，没有parent_wait；等待不计failed时可出现“failed=0”但未完成。

修订：独立持久等待状态与游标，先重试待办再扫描增量；待办生命周期不受overlap裁剪，使用原候选版本并校验源变更。分类计数和告警必须包含等待、失效、未知，不能把零failed当齐套。

### F07 · 高：manifest只做ID过滤，缺少计划要求的约束；对账可绕过apply

- 目前只有table/ids/force实际生效。expected_source_time只是可选地比较since日期前缀，没有逐行源版本校验；目标/来源、revision、摘要、失效、数量上限均未严格验证。
- 实测带错误目标/来源、过期时间、错误摘要、数量上限0的清单，仍发出父请求。
- 同一force清单执行两次，实际调用两次HTTP；无完成记录/断点状态，不能称“同manifest二跑零重复”。
- 清单ID在采集窗中不存在时退出0、发送0，没有精确报告missing目标。
- **更严重：`--table reconcile --replay-manifest ...`不加`--apply`，程序先进入reconcile分支，完全跳过manifest验证，实测仍调用父子HTTP。**本轮全部拦截，不存在真实误发。

修订：所有执行入口先完成统一预检；reconcile+manifest若不支持则明确拒绝，不能静默忽略。默认dry-run对所有组合都零真实副作用。定义严格schema和逐行版本/摘要校验；应用清单需有目标上下文、范围、失效、数量上限及持久执行进度。重放按ID定向取数，逐项报告命中/缺失/漂移；force只能绕过清单内旧幂等，不能绕过父门禁或完成记录。

### F08 · 中高：V13锚点的候选计数和输出粒度错误，不能直接恢复整套v1.3

- V13按`patient_id,test_no,clinic_no`分组后再`COUNT(DISTINCT act.serial_number)`，同一组clinic_no已固定，计数为1不能证明该报告没有其他候选。
- 最终又丢弃patient_id、test_no，只输出serial/type/count；同一就诊的多张检验报告会产生相同serial的多行。
- 对本例当前3张主表按v1.3方式回连V13，实际每张都得到3行，共9行，而其CAND_CNT仍全为1。当前线上主表未使用V13，所以这是**候选修复稿的潜在放大缺陷**，不是声称当前主视图已经9行。

修订：以报告`patient_id+test_no`为归属粒度计算全部候选数；保留报告键及选定就诊键，0/1/N分支明确；N候选显式等待且不任取MIN/MAX。父视图按完整报告键连接，子项使用同一父候选集合，不再独立MAX流水。修复F01时不得直接回滚到这个有放大问题的v1.3文件。

### F09 · 中：验收覆盖和完成声明不匹配

- 冻结selftest日志显示68 checks、0 fail；其新增主要是合成父键适配及失败计数调整，未覆盖上述关键父版本、跨日、跨表ID、队列、manifest路径。
