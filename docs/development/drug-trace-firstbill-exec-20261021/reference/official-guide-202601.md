###  方案1:纯接口方案
建议使用<font style="color:rgb(51, 51, 51);">alibaba.alihealth.drug.yljg.getentinfolist( 企业信息-根据企业名称或证号查询企业信息列表 )</font>接口

1. **<font style="color:rgb(17, 17, 51);">优先通过证件信息查询</font>**<font style="color:rgb(17, 17, 51);">  
</font><font style="color:rgb(17, 17, 51);">使用本地 ERP/WMS/HIS 等系统中客商资料的</font>**<font style="color:rgb(17, 17, 51);">统一社会信用代码</font>**<font style="color:rgb(17, 17, 51);">、</font>**<font style="color:rgb(17, 17, 51);">诊所备案号</font>**<font style="color:rgb(17, 17, 51);">或</font>**<font style="color:rgb(17, 17, 51);">医疗机构执业许可证号</font>**<font style="color:rgb(17, 17, 51);">，调用该接口查询对应的 </font>`<font style="color:rgb(17, 17, 51);background-color:rgba(175, 184, 193, 0.2);">ent_id</font>`<font style="color:rgb(17, 17, 51);"> 与 </font>`<font style="color:rgb(17, 17, 51);background-color:rgba(175, 184, 193, 0.2);">ref_ent_id</font>`<font style="color:rgb(17, 17, 51);">，并将结果缓存至本地系统。</font>
2. **<font style="color:rgb(17, 17, 51);">其次通过客户名称兜底查询</font>**<font style="color:rgb(17, 17, 51);">  
</font><font style="color:rgb(17, 17, 51);">若上述证件信息未能匹配到有效结果，可使用本地系统中的</font>**<font style="color:rgb(17, 17, 51);">客户名称</font>**<font style="color:rgb(17, 17, 51);">再次调用接口进行查询，并将返回的 </font>`<font style="color:rgb(17, 17, 51);background-color:rgba(175, 184, 193, 0.2);">ent_id</font>`<font style="color:rgb(17, 17, 51);"> 与 </font>`<font style="color:rgb(17, 17, 51);background-color:rgba(175, 184, 193, 0.2);">ref_ent_id</font>`<font style="color:rgb(17, 17, 51);"> 缓存至本地系统。</font>

### 在介绍对码方案之前，需要先了解下几个比较重要的概念
+ **追溯码前7位（又称“平台药品标识码”）说明**<font style="color:rgba(17, 17, 51, 0.5);">：</font>

<font style="color:#000000;">通</font>常情况下，追溯码的前7位作为平台层面的**药品标识码**，用于标识某一特定规格的药品。同一药品在不同包装层级（如中盒、大箱）会分配**独立的前7位编码**。当某一前7位对应的码资源耗尽后，系统将为其分配**新的前7位**。因此，一个药品在生命周期内**可能对应多个前7位**，而**每个前7位一般唯一对应一个药品规格**。

在极少数异常场景下（如生产企业贴错码，或生产厂家操作不规范将停止生产的规格直接更新为最新规格时），可能出现**同一个前7位被用于多个不同药品**的情况。此类问题属于非标操作，发生比例极低。如需依赖前7位进行业务判断，建议增加**兜底校验机制**，以规避因前7位复用或错配导致的数据不一致风险。后续方案详述。

+ 药品ID（drugid）：码上放心平台药品的唯一编码，同一个药品同一个规格只有一个药品ID。
+ 69码或者商品条码：由于历史上国家要求的追溯数据集中不包含商品条码，因此，生产厂家维护的商品条码并不全，也不一定准确，因此平台无法准确的提供追溯码与商品条码的映射关系，建议企业根据下述方案，进行两码的映射对照。

### 关于追溯码前7位、平台药品ID与企业内部编码的映射关系说明：
+ **常规情况**：
    - 一个追溯码的**前7位**（平台药品标识码）通常**唯一对应一个平台药品ID**；
    - 而一个**平台药品ID**可能因包装层级变化或码资源轮换，关联**多个不同的前7位**。
+ **异常情况（极少见）**：  
在生产贴码错误或系统异常等特殊场景下，**同一个前7位可能被错误地关联到多个平台药品ID**。此类情况虽比例极低，但需在系统设计中予以考虑。 还有部分特殊药品，短暂发放过8位的标识码，但现在基本上不流通了，可以不考虑这种情况。
+ **企业内部编码的复杂性**：
    - 理想状态下，一个**企业内部编码**应唯一对应一个**平台药品ID**；
    - 但在实际业务中，由于企业主数据管理策略差异，可能出现：
        * **一个内部编码对应多个平台药品ID**（如规格合并管理、历史数据混用）；
        * 或**多个内部编码指向同一个平台药品ID**（如不同部门独立编码、别名管理等）。

单据处理状态查询，**<font style="color:#DF2A3F;">请务必控制调用频率，此接口是最容易出现调用频率超限，出现限流的情况。因此需要做调用失败，隔几分钟后，再调用的处理。</font>**

注意：平台进行了部分成功的改造，需要根据两次字段结合起来判断是否是部分成功。

+ result_type：处理状态 0，处理中 1, 上传成功 3, 处理成功 4, 处理失败
+ sub_process_flag：51全部成功 52部分成功

部分成功的单据， result_type=3处理成功，sub_process_flag=52部分成功

如想切换到整单成功的模式，请在单据上传时，将ignore_part_success_flag修改为1；

码解析策略：1代表整单解析成功(任一码解析失败，上传时整单返回错误),传其他值或者不传代表部分解析成功(跳过无法解析的码，其余正常处理并上传)

单据上传的错误码枚举：[单据上传TOP接口统一返回](https://qg6r2i.yuque.com/qg6r2i/pwz1l1/xrfnhs5kpt7xnudh)，请根据单据错误码处理异常情况

**如果想查看部分成功单据中，失败的码信息可以调用：alibaba.alihealth.drugtrace.top.lsyd.listbillprocesspartsuccess( 部分处理成功单据处理失败的码明细 )**

**<font style="color:#DF2A3F;">部分成功的码需要在平台页面进行处理，操作方法：</font>**[**https://qg6r2i.yuque.com/qg6r2i/hl3e4l/gicxe284d55saqs0?singleDoc#**](https://qg6r2i.yuque.com/qg6r2i/hl3e4l/gicxe284d55saqs0?singleDoc#)**<font style="color:#DF2A3F;"> 《接口上传单据部分解析成功》</font>**

**<font style="color:#DF2A3F;">建议有开发能力的企业，可以进行采用“整单成功”的模式，在本地系统根据报错信息处理相关的异常。</font>**

### 如何确保内部系统的单据与平台的单据一致
建议使用：<font style="color:rgb(51, 51, 51);">alibaba.alihealth.drug.yljg.query.billcount( 查询本企业出入库单数量 )</font>，<font style="color:rgb(51, 51, 51);">alibaba.alihealth.drug.yljg.query.upoutbillcount( 查询上游出库单数量 )</font>，与本地系统进行数量核对，如果单据数量有差异，可以再调用：<font style="color:rgb(51, 51, 51);">alibaba.alihealth.drug.yljg.searchbill( 通过时间段批量查询入出库单信息。 )</font>接口，获取指定时间段内的单据列表明细，再根据单据号比对内部系统与平台的之间的单据差异，在通过接口拉取上游出库单或者重新上传遗漏的单据。
