## 4. A1：digest、源版本幂等与状态持久化

- `PackageRevision.digest` 必须为实际冻结 payload 按仓库既有规范化算法所得完整 SHA256，
  `Submission.snapshot_digest` 与其一致。禁止随意给一个非空串或只对源 ID 哈希。
- 幂等身份独立于每次重写的上传 operationTime：推荐 tenant+target+source_instance+table/id+
  规范化 source_op_time（必要时稳定源内容 digest），保持既有目标唯一约束兼容。
  同一源版本跨不同上传时刻重采仍只产生一笔投递；新源版本产生新不可变快照。
- 同一源时间但内容不同需要显式冲突/版本摘要策略，不能静默覆盖；缺 source_op_time 明确质量失败或
  有依据的稳定版本策略，不能用当前上传时刻伪造源版本。
- 拦截旧源版本要依靠已持久化状态，进程重启/新 Session 后仍有效。sent_state 不能只在内存传一遍。
- 停止 `_shadow_config_db/save_shadow_config` 修改 PUBLISHED ConfigRevision。设计独立运行状态表：
  流水位键至少 tenant+target+source_instance+stream，记录版本状态键至少加 source_record_key；
  行级唯一约束与条件更新避免并发回退。分离 `max_seen/source_cursor` 与 `last_success_version`。
- 可保留旧 ConfigRevision 只读兼容导入：新状态缺失时一次性迁入，重复执行幂等，不删除或改写旧配置。
  首次迁移前后验证旧 revision/content/digest/state 字节语义不变。
- DataPackage/PackageRevision 组织策略需写明：当前是“每批新包、批内 revision 递增”，并非“每源记录 revision=2”。
  可选择稳定业务包+源版本 revision，或保持批包但使用 source_version 独立标识；测试不得把两者混为一谈。
