## 2. S01：先固定调度生命周期契约

在实现和测试中使用以下语义，不把一次 handler 尝试与整个 Job 混为一谈：

| 事件 | Job 状态 | ScheduleRun 状态与时间 |
|---|---|---|
| 创建运行 | PENDING | QUEUED；started_at 为空；保留 fire_time |
| 首次成功领取 | LEASED | RUNNING；首次 started_at；执行 deadline 从此次实际开跑起算 |
| 一次失败待重试 | RETRY_WAIT | 保持 RUNNING；不写 ended_at；不覆盖首次 started_at |
| 重试或租约重新领取 | LEASED | 保留 started_at 和执行 deadline；不得把已观测异常洗回正常 |
| 最终成功 | SUCCEEDED | SUCCEEDED，ended_at 与真实 duration |
| 重试耗尽/不重试失败 | FAILED | FAILED，ended_at 与真实 duration |
| 超时/停滞观察 | 原 Job 不变 | TIMED_OUT/STALLED；不 kill、不释放租约、不放行 FORBID |
| 异常观察后最终结束 | SUCCEEDED/FAILED | 回写最终状态，保留 late 与原观察历史 |

耗时采用 **首次执行至最终结束的墙钟秒数，含重试等待，不含排队等待**。
整数列允许不足 1 秒的真实任务为 0；测试使用受控时钟推进 5 秒，不能 sleep 拼出耗时。
`was_timed_out` 和 `was_stalled` 分别保留，不能对仅 STALLED 的情况无依据地写超时史。

## 3. S02：实际 claim 与最终回写

1. 在 `scheduler.py` 实现 `mark_run_started(db, job, now=None)`；只有带 `schedule_run_id` 的 Job 才处理。
   同时验证 `run.tenant_id == job.tenant_id`、run.job_id/job.id、schedule_id 绑定，错绑定不得写其他租户记录。
2. worker 成功 claim 后、调用领域 handler 前完成并提交首次运行更新；使另一 DB Session 在 handler
   正在执行时能看到 RUNNING。现有 `claim_job` 自己 commit，不能宣称随 claim 原子提交而实际上另开事务。
   可增量使用领取后的事务并记录崩溃窗口，或实现兼容的事务钩子；不要偷偷改变所有调用者的提交约定。
3. 仅首次有效开跑把 `deadline_at` 设为 `start + max_runtime_seconds`。重复领取幂等，重试不无限延长总运行预算。
   `run_guard` 不得用运行时限将尚未开跑的 QUEUED 排队任务标为运行超时；排队积压是另一个观测口径。
4. `finish_job` 的 True 表示该 lease epoch 更新成功，包含 RETRY_WAIT。最小修复是 worker 在 True 后刷新
   Job 状态，只有持久化的 SUCCEEDED/FAILED 才回写业务 Operation 和 ScheduleRun 终态。
   若改返回类型，先清点所有调用者并提供兼容，不可把 False 同时当“租约过期”和“重试中”。
5. 旧 epoch worker 不得改新 owner 的 run 开始/完成信息。异常、正常、特殊 ApiError 分支均审查，
   不能只修最常见异常分支。普通无调度 Job 和 Operation 的既有语义保持。
6. 终态幂等；历史缺 started_at 的旧记录不得伪造 `started_at=ended_at` 再宣称真实耗时。
   对无法还原的历史运行保留 null/明确时间未知标记。只处理本轮正常新运行和安全兼容，不批量改历史账。

## 4. S03：misfire 合并、最近槽位与事务

1. 输入 datetime 先规范为 aware UTC：naive 按 UTC 解释；有 offset 的先 `astimezone(timezone.utc)`，
   落现有 naive UTC 列前再去 tzinfo，不能直接剥离 +08:00。
2. 一次固定 `now_utc`，到期时计算 `future_next = expr.next_after(now_utc)`，严格大于 now。
   next_fire 抢占、run 插入、Job 入队仍同事务，任何一步异常整体回滚；不丢触发、不重复入队。
3. grace 保留当前 120 秒语义，测试正好边界。准点执行原 due 槽位；超 grace 的 SKIP
   仅记一条 MISSED，摘要注明被折叠区间，不制造 96 条历史记录。
4. RUN_ONCE 仅补 `[旧 next_fire_at, now]` 内最近合法槽位。可在 CronExpr 加 `previous_at_or_before`
   或等价纯函数，复用 `matches` 的 Vixie 日/周 OR 语义，设置清晰搜索上限及超限错误。
   不从多年最旧槽位逐次 next_after 遍历；不能直接用 now 冒充最近合法计划时间。
5. 用选出的 fire_time 渲染 `{fire_date}`/`{fire_date_minus_1}`；入队 deadline 从 now 起算，
   首次 claim 再按 S02 固定执行 deadline。blackout 以选中槽位为计划避让，实际 now 也在维护窗口时不启动补跑，
   只记一条 SKIPPED_BLACKOUT；写明两者判定顺序并测试跨午夜。维护窗口不成为延后反复补跑机制。
6. FORBID 仍看真实 Job；TIMED_OUT/STALLED 不能放行重叠。两次相同 now tick 不重复；
   并发条件 UPDATE 失败者 rollback，测试事务失败后下一 tick 能正确重试。

## 5. S04：时区与早报统计窗口

- 建立单一时间规范化函数；`utcnow()` 的 naive UTC 必须先绑定 timezone.utc，再转固定 UTC+8。
  不修改宿主 OS 时区，不引入 tzdata 依赖。
- 昨日窗口取院内昨天 00:00 到今天 00:00，再转换为 UTC 半开区间用于查询。
  昨日新增/恢复告警也用该窗口；若保留滚动 24h 信息，单独标“近24小时”，不可混称昨日。
- 现有 `registry.target_summary(..., days=1)` 是滚动窗口。给摘要层增加向后兼容的显式区间能力，
  或从现有真实台账按窗口聚合；不能只换日期标题。暂不支持自然日的来源必须显示“窗口不可用/仅近24h”，
  不把滚动数字塞进昨日栏。无源数据继续 unavailable/none，ACCEPTED 不升级 CONFIRMED。
- Cron.next_after 参数必须 aware；合法 cron 输出准确院内触发时刻。不只靠 broad except 隐藏编程错误。
  语法错误、搜索范围内无触发和摘要查询异常分别标识；下一次在明天时如实写日期，不硬称今日。
- 未解决告警总数与“展示前10条”分开，排序用统一有效时间；早报落库/文件正文同样经过脱敏。

## 6. S05～S07：告警隔离、入库脱敏与通道

S05：自监控 fingerprint 使用 `alerting.self:{tenant_id}:{rule.code}`，有数据库列长度边界校验。
同规则评估恢复到“没有抛异常”即恢复该规则 self 事件，即使规则本轮仍发现业务问题，也不能继续报告评估器故障。
业务告警仅在证据完整健康时恢复；DATA_UNAVAILABLE/STALE/ERROR 不算健康。
业务恢复循环显式排除 self 事件，两套恢复条件独立；A/B 规则和跨租户不得互相影响。

S06：现有函数叫 `redact_detail`，没有 `sanitize_detail`，可新增后兼容旧调用，不能写一个无调用死函数。
对 finding 的 message/detail、持续更新、self、恢复通知、NotificationLog.error/detail、digest 一并审查。
白名单加实际使用的 error_code/schedule_code/late/unmapped_states/last_notified_at 等安全元数据；
嵌套字典/列表中的字符串继续脱敏，非白名单 payload/SQL/身份信息不透传；限制深度/长度，错误日志不能回显 Secret。
保留冷却时间、ACK 不重复通知、恢复通知语义，避免脱敏丢 last_notified_at 导致通知风暴。

S07：webhook 必填合法 `url_env`，环境变量名符合 `^[A-Z][A-Z0-9_]{2,63}$`；
出现 url/webhook/key/token/secret/password 等内联秘密字段即拒绝，不能因未传 url_env 绕过。
递归检查结构并采用通道专属允许字段，不将任意 `xxx_env` 视为免检通行证。
SMTP 密码仅 password_env；错误响应/审计不回显提交值。历史非法通道不外发、不静默重写配置，显示需修订。
测试创建、更新、test、直接 dispatch：file 正常，smtp/webhook 即使历史 enabled=True 也不得实际网络发送。

## 7. S08：四个接口真实 keyset 分页

| 接口 | 稳定排序键 | 响应迁移 |
|---|---|---|
| GET `/api/v1/schedules/{schedule_id}/runs` | fire_time DESC, id DESC | 保留 schedule/items，增加 next_cursor |
| GET `/api/v1/alerts2` | COALESCE(last_seen_at,created_at) DESC, id DESC | 数组改 items/next_cursor，全部前端调用者同步 |
| GET `/api/v1/notification-logs` | sent_at DESC, id DESC | 补 cursor 参数，数组改分页对象 |
| GET `/api/v1/medins-emr/debug-exchanges` | created_at DESC, id DESC | 数组改分页对象，medins.ts 与历史表同步 |

查询顺序：tenant/scope/归属/筛选 → cursor 条件 → order_by → limit+1。
`ts < c_ts OR (ts=c_ts AND id<c_id)` 在数据库执行，不能取全表后 Python 截断、不能用 OFFSET 冒充游标。
游标使用有版本的 base64 结构，绑定接口资源、租户、目标/schedule、有效 scope 和全部筛选/排序条件；
base64/字段数/版本/时间/ID/大小非法报 400 INVALID_CURSOR，上下文变化报 CURSOR_CONTEXT_MISMATCH。
不得复用现有 decode_cursor 的“坏游标当首页”行为而声称已严格校验。

分页不是安全授权，解码后仍必须重新做 RBAC 与租户筛选。`next_cursor` 只由最后一条实际返回记录生成。
新旧 severity 按 lower 值归一，WARN 覆盖 warn/warning/WARN/Warning；返回统一 INFO/WARN/CRITICAL。
旧 `/api/v1/alerts` 保持数组契约，共享过滤/规范化/排序及 RT-02 的范围防线。
告警 last_seen_at 会变化，明确这是实时列表分页：不承诺并发更新期间的数据库快照；前端按 ID 合并去重，
刷新/改筛选重置游标。在数据静止的验收中必须严格无重无漏。
