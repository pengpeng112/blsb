> 预计工作量：2～3 小时。依赖：RT-01、RT-02、RT-03。动生产：否（传染病影子仅连合成/本地源并只发本机回环 Mock；医保不出网）。

## 0. 背景与目标

独立代码审计查出两个具体上报业务模块（LT-05 传染病纳管、LT-07 山东医保电子病历）存在严重的“半成品/表面交差”和隐私脱敏漏洞：

### A. 传染病模块（`infectious` & `external_ledger`）的 5 个问题
1. **`PackageRevision.digest` 漏填致幂等失效与人工结案崩溃**：`plugins/domains/infectious/send.py:74-82` 创建 `PackageRevision` 时未传 `digest`（默认 `""`），导致 `idem = f"inf:{skey}:{pr.digest[:16]}"` 退化成 `inf:death/1:`（源数据更新 `operationTime` 后仍被当成旧版本跳过！），且 `Submission.snapshot_digest` 为 `""` 被 `report_ledger.py:342` 拒绝人工结案！
2. **取数纯桩（无 `collect.py`）且原地篡改 `PUBLISHED` 配置**：`infectious/plugin.py:42-59` 只读 `job.payload["rows_by_table"]` 内存字典，根本没实现从 SQL 视图按水位+overlap 取数的 `collect.py`；且 `:36-39` `save_shadow_config` 原地修改已发布的 `ConfigRevision`（违反“已发布配置不可变、状态放独立游标表”的铁律），`sent` 次序状态也从未写回持久化。
3. **缺台账详情钩子与文书分类统计**：未注册 `HOOK_LEDGER_DETAIL`，前端点传染病外部台账行返 404；前端业务详情缺按 6 张表/文书类型（死亡/入院/检查/检查项目/首程/日常）的分组统计视图。
4. **缺 7 天影子对账比对工具**：LT-05 承诺的 `compare_shadow_vs_ledger`（对比同一窗口外部台账与平台影子 Submission 的集合差异）未真正闭环。
5. **外部台账导入计数倒挂与 `sent.jsonl` 孤儿记录丢失**：`inf_pusher.py:179-181` `SHAPE_INVALID` 计入 `rows_rejected` 却漏加 `rows_read`（导致 `rows_read < rows_rejected`）；只有 `sent.jsonl` 成功记账而当日 `receipts-*.jsonl` 未导入的记录被 `:240` 直接丢弃。

### B. 山东医保电子病历模块（`medins_emr` & `spec_extract`）的 5 个问题
1. **报告宣称提取 23 个交易，实际只生成了 19 个**：`tools/spec_extract/build_profile.py:208` 只遍历规范接口清单表的 19 项，**`12601—12604`（药品/耗材/诊疗目录与对照上传 4 个交易）根本没生成到 `transactions.json`、`fields/`、`samples/`**！
2. **嵌套报文结构被拍平 + 误混入输出参数表，真实报文校验全错**：
   - 规范 Word 里一个交易有多张子表（如 `patn_bas_info`、`diseinfo` 等输入子节点表，以及最后的**输出参数表**），`build_profile.py:163` 把所有表不分青红皂白全部拍平挂在 `input.<field>` 顶层！
   - 后果：拿一份 100% 合规的真实嵌套报文（如 `{"input": {"patn_bas_info": {"certno": "..."}}}`）去跑 `contract_validator.py`，校验器在顶层报几十个 `REQUIRED` 缺失，而对真正的 `input.patn_bas_info` 报 `UNKNOWN_FIELD` 并直接 `continue` **跳过了内层所有字段的类型/长度/必填校验**！
3. **患者隐私明文落库漏洞（P0 安全）**：
   - `build_profile.py:40-50` 敏感字段识别漏了手机号 `mob` / `tel` / `coner_tel` / `curr_addr` 等常见医保隐私字段；
   - 更严重的是 `plugins/domains/medins_emr/routes.py:35-49` 的 `mask_sensitive` **只遍历脱敏 `input` 顶层第一层标量**！所有嵌套对象（`input.patn_bas_info.certno`、`psn_name`）和数组元素里的患者姓名、身份证号、手机号全部**原封不动明文写入了数据库的 `debug_exchange` 表**！
4. **提取器死代码与脏合成样例**：`build_profile.py:57-60` `"日期" in t` 截胡了 `"日期型"` 导致 `return "date"` 永远走不到；代码标识列 `"Y"` 被当成字典编码写入 `"dict": "Y"`；`dicts` 未传入合成器导致 `opter_type` 生成 `"测试o"`；样例顶层多塞了规范不存在的 `"_synthetic": true` 触发未知字段警告。
5. **联调台前后端脱节**：`MedinsDebug.vue` 历史记录列表里没有“回填院内结果”按钮（只有导出那一瞬间能点）；下载执行包只下了报文 JSON，把后端生成的 `headers` 和参数化请求说明丢掉了；契约表未展示公共报文头 `_envelope.json`。

## 2. 详细实施步骤

### A 段：传染病影子真闭环与外部台账修复

1. **修复 `PackageRevision.digest`、次序状态持久化与不可变配置（`plugins/domains/infectious/`）**：
   - 在 `infectious/send.py` 中：用 `packages/contracts` 或 `core_db` 现有的规范化哈希函数 `digest_of(frozen_payload)` 计算真实 64 位 SHA256 填入 `PackageRevision.digest`！
   - 幂等键采用 `f"inf:{table_key}/{rid}:{source_op_time or pr.digest[:16]}"`：
     * 同一源记录同一 `source_op_time` 重复采集 → 幂等跳过，不重复发送；
     * 同一源记录更新了更大的 `source_op_time` → 生成新 `PackageRevision`（revision 递增，真实非空 `digest`）与新 `Submission`；
     * 乱序到达更旧的 `source_op_time` → 被已持久化的水位/已发版本表显式拦截（记 `skipped_older_version` 统计）。
   - **禁止原地篡改 `PUBLISHED` 的 `ConfigRevision`**！将影子采集的水位（`watermark`）和已发送最大源时间（`sent_op_time`）存入连接器游标表（检查 `core_db/models.py` 现有的 `SourceCursor` / `Connector` 状态表，若无合适行级键值表则新增编号迁移 `021_infectious_shadow_cursor` 建独立小表 `shadow_sync_cursor(tenant_id, target_code, stream_key, watermark, state_json, updated_at)`——先检查最新迁移号避免冲突）！
2. **补齐真正的 SQL 视图增量采集模块 `infectious/collect.py`**：
   - 实现 `collect_from_connection(conn, tables_subset, cursor_store, *, overlap_days_override=None, limit_per_table=500)`：
     * 按依赖顺序（`admission` / `death` / `exam` → `exam_item` → `first_course` → `daily_course`，确保 `exam_item` 能拿到父表 `parent_ops`）从给定的 SQLAlchemy Engine/Connection 查询配置的视图名（测试环境支持 schema 映射或 SQLite 无 `ODS.` 前缀视图/表，如 `V_INF_DEATH_INFO`；生产未来配 Oracle 只读连接器时读 `ODS.V_INF_*`）。
     * 按每表 `watermark - overlap_days`（首次运行按 `full_days`）构造参数化 `WHERE OPERATION_TIME >= :since ORDER BY OPERATION_TIME ASC`，拉取行并交由 `mapping.py` + `send.py` 走完整影子发送链（强制仅发往 `is_mock=True` 本机回环 Mock）。
     * 保留原 `rows_by_table` 内存注入仅作为单测快捷入口，主路径走真实 SQL 查询！
3. **补齐外部台账修复、详情钩子与对账对比工具**：
   - `external_ledger/importers/inf_pusher.py`：
     * 修复 `SHAPE_INVALID` 漏加 `rows_read` 的计数倒挂，确保恒满足 `rows_read == rows_applied + rows_skipped_duplicate + rows_rejected`（或清晰拆分文件行统计）；
     * 当 `sent.jsonl` 中存在某 `table/id` 的成功发送记录、但本次导入的 `receipts-*.jsonl` 未覆盖该条时，生成或补全对应 `external_submission_record`（标记 `last_result="SENT_LEDGER_ONLY"`，桶归入 `ACCEPTED`，并在 `note` 标明“来自 sent.jsonl 本地已发账本”），不静默丢弃！
   - 在 `infectious/hooks.py` 与 `plugin.py` 注册台账单条详情能力（或在 `report_ledger.py` 支持 `external_submission_record` 详情查询）：使 `GET /api/v1/report-center/submissions/inf_cdc_frontend/{id}` 返回该外部台账记录的完整脱敏元数据（业务表、文书编码、源版本时间、最后观测时间、导入批次号、尝试次数、错误码），彻底消灭前端点击行报 404！
   - 在 `infectious/hooks.py` 的 `target_summary` 返回的扩展字段（或新增 `GET /api/v1/report-targets/inf_cdc_frontend/breakdown`）中提供**按 6 类文书表分组的计数表**（死亡/入院/检查/检查项目/首程/日常 × 各状态桶），并在前端 `TargetDetail.vue`（当 `code === 'inf_cdc_frontend'` 时）展示这张文书分类统计表！
   - 实现可实跑的对账函数与 CLI `infectious/reconcile_shadow.py`：`compare_shadow_vs_external(db, tenant_id, date_from, date_to)`，对比同一源时间窗内 `external_submission_record` 与平台影子 `Submission` 的 `table/id` 集合，输出 `{matched, only_in_external, only_in_shadow, version_mismatch}` 报告 JSON。

### B 段：山东医保 23 交易嵌套契约重构、递归全脱敏与联调台完善

1. **重构 `tools/spec_extract/` 并重新生成真 23 交易嵌套契约（`profiles/medins_emr_sd/`）**：
   - **补齐 23/23 交易**：修改 `build_profile.py`，除了接口清单表的 19 个交易外，把正文标题解析出的 **`12601`、`12602`、`12603`、`12604` 四个目录上传交易**一并纳入生成流水线，确保 `transactions.json`、`fields/*.json`、`samples/*.json` 真正达到 **23 个交易一个不缺**！
   - **剔除输出表 + 恢复真实嵌套层级**：
     * 在 `docx_tables.py` / `build_profile.py` 中：识别表格上方的小标题/表头，凡属“输出参数 / 返回参数 / 出参”的表格单独归入 `output_fields`（或跳过不混入 `input` 必填校验）！

   - **修复类型推断、字典标识与干净合成样例**：
     * 修复 `build_profile.py:57-60` 顺序：先判 `"日期时间"` → `"datetime"`，再判 `"日期"` → `"date"`，消灭死代码；
     * 当表格“代码标识”列填的是 `"Y"`/`"是"`/`"1"`（仅表示该字段使用医保标准字典但未给出字典表名）时，设为 `"has_code_dict": true, "dict": null`，不要把 `"Y"` 当成字典名；同时把已提取的 `dicts/opter_type.json` 真正传入合成器，生成合法字典值 `"1"` 而非 `"测试o"`；

2. **升级 `contract_validator.py` 支持完整嵌套对象与数组递归校验**：
   - 当契约节点为 `type: "object"` 或 `type: "array"` 且定义了 `children` 时，递归校验子字段的 `REQUIRED`、`TYPE`、`MAX_LEN`、`DICT`、`FORMAT`（含真实日历校验）；即使同级出现某个 `UNKNOWN_FIELD`（报 WARN），也**绝不跳过**已知子节点的内层校验！
3. **修复患者隐私明文落库漏洞（递归全脱敏，P0 必达）**：
   - 扩充 `build_profile.py` 的敏感字段识别词表：覆盖 `certno`、`psn_cert`、`idcard`、`psn_name`、`opter_name`、`coner_name`、`mob`、`tel`、`phone`、`addr`、`curr_addr`、`emp_name`、`insutype` 关联个人编号 `psn_no`、`medins_file_no` 等所有个人身份/联系信息字段，全部标 `sensitive: true`。
   - 重写 `plugins/domains/medins_emr/routes.py` 的 `mask_sensitive(message, contract)`：
     * **递归遍历任意深度的 dict 与 list**！凡是①契约路径标记了 `sensitive: true`、或②字段键名命中敏感键名正则（如 `name|cert|idcard|mob|tel|phone|addr|cainfo|sign`）、或③字符串值命中 `redact_text` 的身份证/长数字模式，**无论在第几层嵌套、甚至在未知字段里，一律打码脱敏后再写入 `DebugExchange.request_masked` / `response_masked`**！
   - 重新运行并升级敏感值零泄漏扫描脚本：确认 `implementation/profiles`、`implementation/tests`、`implementation/plugins` 对全部 23 个原始样例中的敏感值 **命中数为 0**！
4. **修复前端 `MedinsDebug.vue` 闭环**：
