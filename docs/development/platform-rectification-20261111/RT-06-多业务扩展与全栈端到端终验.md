## 0. 背景与目标

在前 5 个整改长任务把前端崩溃、安全越权、调度/告警内核、传染病/医保业务深度与全站 29 个页面全部打磨到位后，最后一个收官任务要解决审计发现的**平台扩展性与全栈集成终验缺口**：
1. **脚手架只能用一次的 Bug**：`scripts/new_report_target.py:135-137` 用全局唯一的 `SEED_MARK_BEGIN` 注释判重——生成完第 6 个业务后，再执行脚本生成第 7 个业务时会误以为已插入而直接跳过种子追加！且 `:115` 对 `plugin_key` 用全文字符串包含判断易误判，`:36` 在 Windows 下未拦截正斜杠 `/` 路径穿越。
2. **济南医保影像云（`medins_imaging_jn`）仅有空壳 CSV 清单**：`tools/spec_extract/csv_profile.py` 生成的 16 张表契约全部是无必填、无类型的空壳，且 `plugins/domains/medins_imaging/` 只有返回 `none` 的空桩，未能展示“一个新上报业务如何利用本平台的 Profile + 契约校验 + 视图发布/Mock 推送 + 统一台账跑通闭环”。
3. **病理云 79 位正式索引编码规范（`93ebd53751dc40669f4c977781904f8b.txt`）对齐**：根目录已有国家医保局正式印发的 8 段 79 位（含分隔横线 86 字符）病理云索引编码说明，而 `pathology/index_codec.py` 对横线分隔格式与院内编码规则缺乏清晰的可配置兼容与校验说明。
4. **缺少前后端真实 HTTP 联调端到端（E2E API）冒烟验证**：此前前端与后端各自测自己的，导致 URL/字段错配漏网。需要一套自动化全栈契约冒烟测试，真实拉起 FastAPI 应用 + SQLite 测试库 + Worker 执行一轮 tick，用前端 `src/api/*.ts` 定义的完全一致的请求路径与参数走通全站所有模块接口！

## 2. 详细实施步骤

### 步骤 1：彻底修复新业务接入脚手架 `scripts/new_report_target.py`

1. **支持无限次追加第 6、第 7、第 N 个新上报业务**：
   - 将判重条件从检查固定的 `SEED_MARK_BEGIN` 改为检查专属标记 `f"# <scaffold-target:{code}>"` 或精确解析 `DEFAULT_TARGETS` 列表中已有的 `"code": "..."` 字典键！
   - 插入位置改为锚定在列表尾部的 `# === SCAFFOLD_INSERT_ANCHOR ===` 注释上方（每次插入后保留锚点注释不消费掉），从而支持连续创建第 6、第 7、第 8 个新业务，且同一个 `code` 重复运行严格幂等跳过！
2. **修复精确匹配与路径穿越防护**：
   - 检查 `plugin_key` 是否已绑定时，限定在对应 `code` 的字典块内匹配 `"plugin_key": "..."`，不全文盲搜；
   - `--biz-dir` 参数同时拦截 `\`、`/`、`..`、盘符 `:` 与首尾空白，确保在 Windows 与 Linux 下均无法跳出 `数据上报/` 目录；
   - 生成的路由骨架自动使用 RT-02 建立的 `reg.attach("domain.routes", register_routes)` 标准机制。
3. **单测证明**：在临时工作区副本中连续调用脚手架创建 **2 个不同新业务**（`demo_target_a` 和 `demo_target_b`），断言 2 个业务均成功写入种子列表、manifest 均可发现、重复调用第 2 次零修改！

### 步骤 2：充实济南医保影像云（`medins_imaging_jn`）契约与示范闭环

1. **增强 `csv_profile.py` 与 `profiles/medins_imaging_jn/`**：
   - 重新读取 `设计交付v0.4/契约与示例/PACS_V2_字段清单_原样提取.csv`（及 `pacs接口上传说明/` 下的规范说明如有可读文本，注意离线只读不改原件）：提取 CSV 中已有的全部列元数据（数据集编码、数据集名称、字段英文名、字段中文名、备注/类型线索），对日期时间类字段标注 `format`、对姓名/身份证/电话标注 `sensitive: true`，生成带完整中文字段名与合成演示样例 `samples/<dataset>.json` 的 16 个数据集 Profile（仍如实保留 `unconfirmed` 标记：凡 CSV 未给出的必填/长度均显式标 `SPEC_FIELD_CONSTRAINT_PENDING`，不瞎编长度）。
2. **升级 `plugins/domains/medins_imaging/` 示范能力**：
   - 挂载轻量只读契约与本地模拟校验路由 `/api/v1/medins-imaging/datasets`、`/api/v1/medins-imaging/validate`（含 `p.require_target_scope("medins_imaging_jn")` 鉴权！），复用 `contract_validator` 支持对 16 个数据集（含已实现的 `chk_info`、`asset_info` 投影结构）做本地契约预检与 Mock 投递演练。
   - 实现 `target_summary` 与 `ledger_search` 钩子（查询关联 `medins_imaging_jn` 的通用 Mock `Submission` / `Publication`，无记录时返回 `data_source="none"`），证明新生成的插件无需改动任何平台核心文件即可自动接入驾驶舱、业务详情和统一提交台账！

### 步骤 3：病理云 79 位编码规范（`93ebd537...txt`）只读对齐校验

1. 阅读根目录 `93ebd53751dc40669f4c977781904f8b.txt`（国家医保局病理云索引编码规则：8 段组成，纯码段共 79 位，带 `-` 连接符共 86 字符）。
2. 在 `plugins/domains/pathology/index_codec.py` 中（**严禁改动既有函数返回值或放松 `CANDIDATE_UNCONFIRMED` 门禁**！确保既有 43 个探针与病理测试 100% 不受影响）：
   - 新增纯辅助校验/格式化函数 `format_nhsa_pathology_index(segments, *, with_hyphen: bool = True) -> str` 与 `parse_nhsa_pathology_index(code: str) -> dict`：支持 79 位紧凑格式与 86 位带 `-` 标准展示格式双向无损解析与段长校验（第 1～8 段精确位数核验），供病理工作台与后续正式协议 B09 落地直接调用；
   - 更新 `数据上报/3、病理上报/README.md`，写明 79 位/86 位编码辅助工具位置与 B09 外部阻断现状。

### 步骤 4：编写全栈端到端契约冒烟测试 `tests/e2e/test_fullstack_console_smoke.py`

这是整套平台演进与整改的**总验收守门员**：
1. 在单个集成/E2E 测试套件中，使用全新临时 SQLite 库执行完整 `migrate`（001→最新）+ `bootstrap`（种子初始化，含 5 个默认上报业务、镜像调度、默认规则与本地文件通道）。
2. 启动 FastAPI `TestClient` + `WorkerEngine`：
   - **认证与权限链**：管理员登录 → `/auth/me`（校验 `roles` 与 `target_scopes`）→ 创建受限业务运维员 `op_dt`（仅授权 `drug_trace_alihealth`）→ 验证 `op_dt` 访问驾驶舱/业务列表只看到授权项，访问 `/medins-emr/*` 返回 403！
   - **五大业务全景链**：
     1. 码上放心：只读拉取 summary 与台账，验证状态桶与积压字段完整；
     2. 传染病：通过 `/report-center/external-imports` 先 dry-run 再正式导入合成副本 → 验证驾驶舱卡片、6 类文书分类统计、台账检索与行详情 200；再跑一轮影子 SQL 采集+本机回环 Mock 发送 → 验证 `PackageRevision.digest` 非空与影子对账报告；
     3. 山东医保电子病历：拉取 23 交易列表 → 校验嵌套报文 → 发送 Mock → 导出执行包 → 历史记录回填结果 → 查库确认敏感字段 0 明文泄漏；
     4. 济南医保影像云：拉取 16 数据集契约 → 跑 `chk_info` 模拟校验；
     5. 病理云：跑合成病例归集/质量/冻结/Mock 发布 + 79/86 位编码解析校验。
   - **调度、运行治理与告警早报链**：新建一条测试用本地 Mock 调度 → `enable` → `run-now` → Worker `tick` 执行完成 → 验证 `ScheduleRun` 经历 `RUNNING` 到 `SUCCEEDED` 且 `duration_seconds >= 0` → 执行一轮 `alert_evaluate` 与 `alert_digest` → 验证早报生成成功且无“表达式待核”、本地文件通道产出 JSONL、告警 `ack` 产生 `AuditEvent` → 审计 CSV 导出成功带 UTF-8 BOM！
3. **静态交叉校验前端 API 路径**：写一个测试解析 `apps/admin_web/src/api/*.ts` 中所有 `/api/v1/...` 路径模板，与 FastAPI `app.routes` 注册的真实路径 + HTTP 方法逐一比对，**断言前端调用的每一个后端 API 路径在 `app.routes` 中 100% 真实存在（0 个幽灵 404 接口）**！
