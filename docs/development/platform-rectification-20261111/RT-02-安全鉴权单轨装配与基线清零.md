## 0. 背景与目标

独立代码审计发现后端安全、插件装配与测试基线存在以下突出隐患：
1. **4 处高危 `target_scopes` 越权绕过**：
   - `plugins/domains/medins_emr/routes.py:71-267` 全部 7 个 `/api/v1/medins-emr/*` 端点**零调用** `p.require_target_scope("medins_emr_sd")`；
   - `apps/core_api/report_target_routes.py:99-115` `PUT /api/v1/report-targets/{code}` 漏调 `require_target_scope(code)`，受限 `config_editor` 可篡改全院任意业务状态；
   - `apps/core_api/ops_routes.py:308-329` `PUT /api/v1/alert-rules/{code}` 未校验该规则所属业务与系统级规则权限；
   - 旧接口 `/api/v1/alerts`（`app.py:2255`）与 `/api/v1/submissions`（`app.py:1706`）未按 `target_scopes` 收缩，受限账号可绕过新接口读取全租户数据。
2. **运维写操作漏写审计 & 最后管理员并发归零竞态**：
   - `ops_routes.py` 中告警确认/关闭、规则新建/更新、通知通道新建/更新全部漏写 `AuditEvent`；
   - `system_routes.py:162-177` 仅单行锁 `subject.id`，双管理员并发互相/自我降权会导致全租户 `platform_admin` 归零，且计数未过滤 `status == "ACTIVE"`（已锁定账号 `locked_until > now` 仍充数）。
3. **插件双轨制分裂与生产 Compose 断裂**：
   - `BLYB_PLUGINS` 未设置时，`app.py:143-164` 与 `worker/engine.py:820-827` 走旧 `plugin_registry`，令 `_loaded_registry = None`，导致 `ops_routes` 收到 `None` 丢失全部领域任务类型（`known_job_types` 无 `drug_trace.*` / `inf.*`）；且 `app.py:1682` 硬编码 `medins_emr` 挂载，未消费插件注册的 `"domain.routes"` 能力；
   - `deploy/compose/drug-trace.override.yml` 只覆盖了 `core` 和 `worker` 的 `BLYB_PLUGINS`，**漏了 `migrate` 和 `bootstrap` 服务**，会导致迁移或镜像种子漏跑！
4. **长期遗留的测试红项与 3453 条弃用警告**：
   - 复核探针 `test_R22_oracle_can_initialize_with_configured_driver_and_dsn` 长期失败（42/43）；
   - `test_drug_trace_pg.py` 硬编码端口 `55432` 冲突报错 + 断言漏掉新迁移号；
   - SQLAlchemy 2.0 弃用 API（`Table.tometadata`、`db.query(...).get(...)`、SQLite 默认 datetime 适配器）刷屏 3453 条警告。

本任务目标：**堵死全部越权漏洞与并发竞态、补齐全部运维审计、打通 `app_runtime` 单轨插件装配与 Compose 一致性、让探针达到 43/43 全绿、消除 PG 测试双 Bug 并大幅清理 SQLAlchemy 弃用警告**。

## 2. 详细实施步骤

### 步骤 1：堵死全部 `target_scopes` 越权漏洞（先鉴权后查库，403 优先于 404 防枚举）

1. **`plugins/domains/medins_emr/routes.py`**：
   - 在全部 7 个接口入口拿到 `p = ctx.require_principal()` 后，**第一行立即调用 `p.require_target_scope("medins_emr_sd")`**（注意：机器 token / `platform_admin` / `["*"]` 在 `Principal.require_target_scope` 中原本已放行，先核对 `contracts/api.py` 确认既有兼容语义不变）。
2. **`apps/core_api/report_target_routes.py`**：
   - `PUT /api/v1/report-targets/{code}`：入口立即调用 `p.require_target_scope(code)`！防止受限 `config_editor` 修改未授权业务。
   - `POST /api/v1/report-targets`（新建业务）：仅 `platform_admin` 且必须具备全局范围（`p.require_global_scope()` 或 `"*" in p.target_scopes`）。
3. **`apps/core_api/ops_routes.py`**：
   - `PUT /api/v1/alert-rules/{code}` 与 `POST /api/v1/alert-rules`：
     * 修改规则时：先查出数据库中原规则的 `old_target = rule.target_code`，若 `old_target == ""`（系统全局规则）则要求全局范围（非受限用户，否则 403），若 `old_target` 非空则 `p.require_target_scope(old_target)`；同时若请求体试图把 `target_code` 改为新值 `new_target`，对 `new_target` 同样执行校验！
     * 新建规则时：`target_code == ""` 要求全局范围，非空要求 `p.require_target_scope(target_code)`。
   - 核查 `ops_routes.py` 其余所有调度（`enable`/`disable`/`run-now`/`PUT`/`runs`）与告警（`ack`/`resolve`）接口，确认每一处对 `target_code == ""`（系统级）都拒绝仅持单业务 scope 的受限账号操作。
4. **旧接口范围收缩（`apps/core_api/app.py`）**：
   - 检查 `Principal`：当主体是受限人类控制台账号（即非机器 service 主体、非 `platform_admin`、且 `target_scopes` 不含 `"*"`）时：
     * `GET /api/v1/alerts`：只返回 `AlertEvent.target_code.in_(p.target_scopes)` 的记录（若 `target_scopes` 为空则返回空列表 `[]`）；
     * `GET /api/v1/submissions` 与 `GET /api/v1/submissions/{sid}`：按 `Destination` 关联的 `ReportTarget` 过滤，不允许受限账号通过旧接口跨业务偷看提交记录（保持机器 token 和既有 `["*"]` 管理员行为 100% 不变！）。

### 步骤 2：补齐运维写操作审计日志 + 修复最后管理员并发锁

1. **`apps/core_api/ops_routes.py` 审计全覆盖**：
   - 为以下 6 类写操作全部补写 `AuditEvent`（actor=p.subject_code，trace_id=ctx.request_id，记录变更前后关键字段快照，严禁记录任何敏感值，理由写入 `reason`）：
     * `alert.ack`（告警确认）
     * `alert.resolve`（告警人工关闭）
     * `alert_rule.create` / `alert_rule.update`
     * `notification_channel.create` / `notification_channel.update`
   - 核对调度的 `create`/`update`/`enable`/`disable`/`run_now` 是否均已写 `AuditEvent`，有漏一并补齐。
2. **`apps/core_api/system_routes.py` 修复最后管理员并发归零竞态**：
   - 在修改用户角色（移除 `platform_admin`）或锁定管理员账号时：**不要只 `FOR UPDATE` 当前被改的一行**！改为先按 `id` 升序查询并锁定该租户下所有有效管理员行：
     `admins = db.query(AuthSubject).filter_by(tenant_id=tid, status="ACTIVE").order_by(AuthSubject.id).with_for_update().all()`，再在内存过滤出含 `ROLE_PLATFORM_ADMIN` 且对应的 `ConsoleAccount` 未处于锁定态（`locked_until is None or locked_until <= now`）的活跃管理员集合！
   - 若本次操作后剩余活跃未锁定 `platform_admin` 数量 `< 1`，立即抛出 `ApiError("CONFLICT", "不能移除或锁定最后一名活跃平台管理员")`！这样在 PostgreSQL 下行锁覆盖全体候选管理员，彻底杜绝双管理员并发自我降权归零。

### 步骤 3：统一 `app_runtime` 单轨装配与生产 Compose 一致性

1. **消除 `_loaded_registry = None` 断层（`apps/core_api/app.py` & `apps/worker/engine.py`）**：
   - 先仔细检查现有测试（搜 `BLYB_PLUGINS` 与 `plugin_registry`）为什么当初保留双分支：旧测试在未设 `BLYB_PLUGINS` 时期望只启用 `pathology,metrics` 还是全量？
   - **稳妥根治做法**：
     * 让 `app.py` 和 `worker/engine.py` **始终拥有非空的 `_loaded_registry: PluginRegistry` 实例**！当环境变量 `BLYB_PLUGINS` 显式设置时调用 `app_runtime.load_registry()`；当未设置时，调用 `app_runtime.load_registry(["pathology", "metrics"])`（或与旧默认完全一致的列表，但同时确保旧 `plugin_registry` 模块导出函数委托给同一套处理器，不产生两套分裂表）！
     * 这样 `ops_routes.register(..., _loaded_registry)` 永远拿到真实的 `PluginRegistry` 对象，绝不会收到 `None`！
     * 将 `app.py:1682` 硬编码的 `if _loaded_registry and _loaded_registry.has("medins_emr"): from domains.medins_emr...` 改为通用机制：遍历 `_loaded_registry.capability_list("domain.routes")`，依次调用插件自己注册的路由挂载函数 `fn(app, sf, auth, _loaded_registry)`！未来任何新业务插件（如 `medins_imaging`）只需在自己的 `plugin.py` 里 `reg.attach("domain.routes", register_routes)` 即可自动挂载路由，核心 `app.py` 再也不用改一行代码！
2. **修复 `deploy/compose/drug-trace.override.yml` 与 `DEPLOY_RUNBOOK.md`**：
   - 在 `deploy/compose/drug-trace.override.yml` 中：为 `migrate` 和 `bootstrap` 两个服务补齐与 `core`/`worker` 完全相同的 `BLYB_PLUGINS: ${BLYB_PLUGINS_DRUGTRACE:-pathology,metrics,drug_trace,infectious,medins_emr,medins_imaging}` 环境变量！（注：`infectious`、`medins_emr`、`medins_imaging` 三个新插件均无自启生产任务、无真实外发权限，默认纳入 override 后生产升级即可直接使用传染病外部台账面板与医保联调台，同时通过 `${BLYB_PLUGINS_DRUGTRACE:-...}` 支持运维随时按需收缩）。
   - 同步更新 `docs/development/platform-evolution-20261103/DEPLOY_RUNBOOK.md` 中关于 `BLYB_PLUGINS` 与 `migrate/bootstrap` 一致性的说明。

### 步骤 4：修复探针 `R22`（达成 43/43 全绿）、修复 `test_drug_trace_pg` 双 Bug 与清理 SQLAlchemy 2.0 弃用警告

1. **修复探针 `R22`（严禁改 `test_review_probes.py`！）**：
   - 根因：`test_review_probes.py:349-351` 往 `sys.modules["oracledb"]` 塞了一个 `SimpleNamespace(connect=lambda *a, **k: None)`（模拟已安装轻量驱动桩，没有 `init_oracle_client` 属性），然后调用 `OracleWarehouse()` 期望能成功初始化（或测连接配置），而 `plugins/sources/db_view/oracle_client.py:62` 无条件调 `oracledb.init_oracle_client(lib_dir=lib_dir)` 抛 `AttributeError`，且把错误粘滞在全局 `_state["error"]` 中！
   - 修复 `plugins/sources/db_view/oracle_client.py`：
     * 检查 `init_fn = getattr(oracledb, "init_oracle_client", None)`：若导入的 `oracledb` 对象不是标准真实 C/Python 驱动模块（例如测试注入的无 `init_oracle_client` 桩对象 `!callable(init_fn)` 且没有 `__version__`/`DatabaseError`），识别为 synthetic test stub：不缓存到进程级永久粘滞 `_state`（避免污染后续测试），直接返回 `("stub", None)` 允许 `OracleWarehouse` 完成构造；而对真实的 `oracledb` 模块（`callable(init_fn)`），**100% 保持原有 Thick 初始化强制要求与失败阻断语义一字不改**（写专门单测验证：真实 `oracledb` 的 `init_oracle_client` 抛异常时仍然严格抛 `CapabilityError("DRIVER_UNAVAILABLE")`）！
2. **修复 `tests/integration/test_drug_trace_pg.py` 双 Bug**：
   - Bug 1：端口硬编码 `55432` 与宿主已有容器冲突，且 `docker run` 失败时未清理同名残留容器。改为用 `socket` 动态分配本机空闲端口（`bind(('127.0.0.1', 0))` 获取端口），容器名加随机后缀并在 `finally` 中 `docker rm -f`；若本机 Docker daemon 未运行或无 `postgres` 本地镜像（离线不拉取：加 `--pull=never`），则干净地 `pytest.skip("local postgres docker image unavailable offline")`，**绝不产生 `ERROR` 或泄漏僵尸容器**！
   - Bug 2：更新第 82-83 行迁移集合断言，纳入药品插件已合法注册的性能索引迁移（如 `020_drug_trace_perf_indexes` / 实际名称以代码为准），消除端口修好后的 `AssertionError`。
3. **清理 SQLAlchemy 2.0 与 Python 3.12+ 弃用警告（3453 warnings → 趋近 0）**：
   - `packages/core_db/migrate.py:42` 与 `plugins/domains/pathology/models.py:248`：将 `t.tometadata(md)` 替换为 SQLAlchemy 2.0 标准 `t.to_metadata(md)`（一处改动即可消除 ~2900 条警告！）。
   - 在 `plugins/core_handlers.py`、`apps/worker/engine.py`、`plugins/domains/pathology/pipeline.py`（及全局搜 `.query(` 后紧跟 `.get(` 的位置）：将遗留的 `db.query(Model).get(pk)` 替换为 `db.get(Model, pk)`（注意 `pk is None` 时 `db.get` 需先判空 `db.get(Model, pk) if pk is not None else None`）。
