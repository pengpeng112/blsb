# 待审方案：HIS 追溯主表函数索引（FBI）可行性

## 一、用户原始需求（原话）

- 2026-10-31："请你看看 调用codex分析创建的索引是否可以"
- 背景需求原话（2026-10-29/31）："请你连接数据库看看给出优化视图 但是不要影响结构"；
  "可以改下视图不加索引吗 你好好分析下 给出修改视图的方案 但是看看不要影响结果"。

## 二、背景（全部有实测证据，见 §五文件指针）

药品追溯日批（每日凌晨采集昨日全窗口→逐单发送到"码上放心"平台）连续多日失败：采集需 ~6h
（HIS 查询均速 1.7→3.5s/次），超过驱动 4h 采集等待上限。根因已实测定位：
- 应用按 `source_bill_id`（= `TO_CHAR(PRESC_DATE,'YYYY-MM-DD HH24:MI:SS')||'|'||TO_CHAR(PRESC_NO)||'|'||DISPENSARY`
  三列拼接串）等值查询视图 → 拼接谓词无索引可服务 → 每单查询全表扫 `PHARMACY.DRUG_PRESC_MASTER`
  （Oracle 11g，702 万行/21.5 万块）；
- 码视图连接 `T.TRACE_BILLNO = TO_CHAR(M.PRESC_NO)` 函数落在索引列侧。
- 分解谓词实测毫秒级（`MED_TRACE_RECORD` 的 `med_trace_record_trace_billno(TRACE_BILLNO)` 索引、
  主表 PK 均已存在）——正确访问路径本来就在。
- 已实测排除"只改视图不加索引"：拼接等值谓词无视图文本解法；外层对视图加 hint 无效；
  视图内嵌 hint 无法只读预验证且只救一半负载。

## 三、待审方案（唯一改动：一个函数索引；视图/应用/表结构零改动）

```sql
CREATE INDEX PHARMACY.IX_DT_BILLKEY ON PHARMACY.DRUG_PRESC_MASTER(
    TO_CHAR(PRESC_DATE,'YYYY-MM-DD HH24:MI:SS') || '|' || TO_CHAR(PRESC_NO) || '|' || DISPENSARY)
  ONLINE TABLESPACE <索引表空间>;
```

配套视图定义（视图 `V_DRUG_TRACE_BILL.source_bill_id` 与索引表达式逐字符一致）：

```sql
CREATE OR REPLACE VIEW PHARMACY.V_DRUG_TRACE_BILL AS
SELECT
    CAST('HIS' AS VARCHAR2(16)) AS source_system,
    TO_CHAR(M.PRESC_DATE, 'YYYY-MM-DD HH24:MI:SS')
        || '|' || TO_CHAR(M.PRESC_NO)
        || '|' || M.DISPENSARY AS source_bill_id,
    -- ...（其余列略，见 repo 内完整 DDL）
FROM PHARMACY.DRUG_PRESC_MASTER M
WITH READ ONLY;
```

应用查询模板（不可改，采集逐单执行）：

```sql
SELECT ... FROM V_DRUG_TRACE_BILL
WHERE source_system = :ss AND pharmacy_code = :pc
  AND business_kind = :bk AND source_bill_id = :sb;
-- 码视图同理（V_DRUG_TRACE_CODE，T JOIN M）
```

## 四、实测证据（2026-10-29/31，平台只读账号 + 生产 worker 账号）

| 查询 | 净耗时 |
|---|---|
| poll 窗口（updated_at 范围，走 IDX_DISPENSING_DATETIME） | ≈0s |
| 单头按 source_bill_id 等值（视图） | ~1.1s（全表扫） |
| 码明细按 source_bill_id 等值（视图） | ~1.0s（双表扫） |
| 同单 T 侧分解谓词（TRACE_BILLNO+PRESC_DATE+STORE_CODE） | 毫秒 |
| 同单 M 侧 PK 分解谓词（PRESC_DATE+PRESC_NO） | 毫秒 |
| 外层对视图加 hint（LEADING/USE_NL/INDEX） | 无效果 |

表规模：M=7,027,460 行；T(MED_TRACE_RECORD)=8,392,907 行。日增约 3 千行。
现有索引：M 有 PK(PRESC_DATE,PRESC_NO)、PK_DIS(PRESC_DATE,PRESC_NO,DISPENSING_DATETIME,DISPENSARY)、
IDX_DISPENSING_DATETIME、INDEX_01(PRESC_NO)；T 有 trace_billno、T_TRACE_CODE、PK(RECORD_ID)。

## 五、请自由分析的问题（不限于）

1. 该 FBI 在 Oracle 11g 上是否可行/正确（TO_CHAR(NUMBER) 无格式掩码在 FBI 中的确定性与 NLS 风险、
   表达式与视图列逐字符一致才能被优化器匹配的前提是否成立）；
2. NLS 风险的具体面：会话 NLS_NUMERIC_CHARACTERS/NLS_DATE_LANGUAGE 差异是否会使索引不被使用或
   结果错误；DBA 建索引与应用会话（python-oracledb thick，容器内）NLS 不一致的现实风险与验证方法；
3. 写入代价/空间估算是否可接受；ONLINE 建索引在 11g 的限制与风险；
4. 是否有更优的索引表达式或替代设计（含"为什么不建 (PRESC_DATE,PRESC_NO,DISPENSARY) 普通复合索引
   +改应用模板"的对比）；
5. 任何你自发发现的问题（正确性/安全/运维/一致性，任何维度）。
