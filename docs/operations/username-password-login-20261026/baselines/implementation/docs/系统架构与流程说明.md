# 系统架构与流程说明（通俗版）

> 目标读者：项目相关方、新加入的开发/实施/运维人员。不需要读代码就能看懂这套系统
> 是什么、怎么运转、边界在哪。技术细节见 `docs/` 下其他文档。
> 更新：2026-10-09。

---

## 1. 这个系统是干什么的

医院每天产生三类数据：**病理扫描的大文件**（WSI 切片、标签图，动辄几百 MB 到 GB）、
**业务系统里的结构化记录**（PIS 病理系统的病例/玻片/报告，HIS 的患者/就诊）、
**运营指标**（月度统计等）。这些数据最终要按要求**上报给医保平台等外部系统**。

本系统就是那条"**传送带 + 质检车间 + 台账**"：

> 把院内各种来源的数据安全地收进来 → 和正确的患者对上号 → 质量检查 →
> 打包冻结（不可变）→ 上报到外部平台 → 收回执、留证据、可对账。

一句话：**不只把数据"搬过去"，还要保证搬的是对的、错了能改、全程有据可查。**

---

## 2. 为什么不"直接传"

如果只是把文件从 A 搬到 B，一个脚本就够了。但医院上报场景有几个绕不开的现实：

1. **对方要证据**——报出去了要拿到"确认回执"才算完成；对方不回，你得知道怎么查证、怎么补偿，且不能重复上报。
2. **数据有坑**——条码可能一对多、病理号有前导零、患者和就诊是两回事、字典值要经过批准才能映射。猜错一个，报上去就是错账。
3. **故障是常态**——院内网络会断、程序会崩、对方接口会超时。任何一种都不能造成丢数据或重复上报。
4. **报出去的东西不能偷偷改**——发现报错了，正确做法是"发一个更正版本"，而不是改历史。

这套系统的全部设计，都是围绕这四条现实展开的。

## 3. 整体架构：五个角色

把系统想象成一家有明确分工的物流+质检公司：

```
 扫描工作站(医院科室)          服务器（院内机房/单机）                外部
─────────────────      ─────────────────────────────────      ─────────
                     ┌──────────────────────────────────┐
 扫描仪落盘文件  →   │ 采集员 Agent（工作站常驻小程序）    │
                     │  盯目录、本地记账、断点续传         │
                     └──────────────┬───────────────────┘
                                    │ 分片上传（每片带指纹）
                     ┌──────────────▼───────────────────┐
                     │ 仓库管理员 storage（:8001）        │
                     │ 收片、校验、合并成正式资产、管配额   │
                     └──────────────┬───────────────────┘
                                    │ 文件就绪
   ┌────────────────────────────────▼────────────────────────────────┐
   │ 业务中枢 core（:8000）—— 挂号、对号入座、质检、审批、台账          │
   │  · 病例关联（条码反查 PIS）  · 质量门禁（12条规则）                │
   │  · 人工复核（歧义/冲突转人工）· 配置治理（连接器/字典/流程/配置包） │
   │  · 审计（只追加）           · 控制台网页（/ui/）与接口文档（/docs） │
   └───────┬───────────────────────────────────────────┬─────────────┘
           │ 冻结包                                       │ 已发布快照
   ┌───────▼──────────┐                          ┌───────▼─────────────┐
   │ 流水线工人 worker │  推送(PUSH)→模拟医保平台    │ 外联窗口 exchange    │
   │ 领任务、重试、    │◄────────────────────────── │ （:8002）只读货架、  │
   │ 等回执、轮询退避  │        回执                 │ 文件下载、收回执     │
   └──────────────────┘                          └─────────────────────┘
```

| 角色 | 程序 | 地址 | 一句话职责 |
|---|---|---|---|
| 采集员 | edge_agent | 装在扫描工作站 | 文件齐了（有厂商完成清单）才登记；本地 SQLite 记账，断网不丢，恢复只补缺片 |
| 仓库管理员 | storage_service | :8001 | 大文件按分片收货、逐片验指纹、收齐合并成不可变的"资产"；重复交货认账不重复入库；管磁盘配额 |
| 业务中枢 | core_api | :8000 | 数据和人对上号、质量把关、人工审批、配置管理、审计；控制台网页也由它托管 |
| 外联窗口 | exchange_gateway | :8002 | 对外提供"只读货架"：外部系统按发布快照拉数据、下载文件、交回执 |
| 流水线工人 | worker | 常驻进程 | 从任务清单领活：关联重试、冻结打包、推送、等回执、指数退避轮询——不占线程死等 |
| 模拟医保平台 | mock | :8090 | 演练对手盘（可模拟超时/拒收/不回执等 9 种行为），**显著标注非真实平台** |

**两处关键设计**：

- **插件化**：病理只是第一个业务插件（`plugins/domains/pathology`），指标是第二个
  （`metrics`，仅 83 行接入完整上报链路）。以后接新数据域 = 写新插件，核心不动。
- **数据存储**：开发/演示用单文件 SQLite（零安装）；生产换 PostgreSQL（同一套代码，
  改一个配置）。前端构建后由 core 直接托管在 `/ui/`，单机部署不需要额外前端服务器。

## 4. 一张玻片数据的完整旅程（核心流程）

以病理为例，从扫描仪到医保确认，一共十步。**每一步都可能"停住等待"，但绝不瞎猜**：

1. **扫描完成**：扫描仪在工作站落盘 大文件 + 标签图 + 一份"完成清单"（manifest，
   记录有哪些文件、各自大小和指纹）。
2. **采集员发现**：Agent 巡检目录，核对清单与实际文件一致后登记事件。同一扫描
   不会重复登记；文件还在变化就先不动（稳定窗口不能证明完成，必须有清单）。
3. **分片上传**：大文件切成片（默认 64MB，可调）逐片传输，每片带 sha256 指纹。
   断网中断后重启，只补缺的片，已确认的片不重传。
4. **收货合并**：全部到齐 → 合并 → 整文件指纹复核 → 通过即成为正式**资产**（不可变，
   入库去重）；不通过则隔离留证并释放磁盘预留。资产状态在"文件资产"页可见。
5. **对号入座**：扫描件通常只带条码。服务端拿条码反查 PIS：
   - 0 条候选 → 等待（PIS 数据可能还没到），PIS 更新后被唤醒重试；
   - 多条候选 → **转人工**，绝不自动取第一条；
   - 唯一命中 → 自动绑定玻片。
   同时患者身份（HIS）和就诊记录分开核对——没有已确认的就诊号就不选"最新一次住院"。
6. **质检**：12 条质量规则（日期合理性、证件冲突、字典是否批准、玻片是否齐套…）。
   不达标不进入下一步，问题进"质量队列"等人工处理或等外部数据补齐。
7. **冻结打包**：条件满足后生成**上报包**（带整体指纹，内容从此不可变）。
   以后发现报错了 → 发**新版本**，历史版本原样保留。
8. **双路上报**：推送（PUSH 到平台）和货架发布（对方按快照来拉）同时进行，
   两路状态独立记录，互不覆盖。
9. **等回执**：按指数退避（1s→2s→…封顶 60s）轮询回执，避免打爆对方。
   **拿到 CONFIRMED 才把病例标为"目标确认"**；没回执就只是"已发送"，
   界面上绝不显示"医保成功"。
10. **对账留痕**：随时可生成"本地状态 vs 对方回执"的差异快照，差异项走补偿
    （按原幂等键查证/重发），不盲目全量重传。所有人工操作、下载、登录进审计，
    审计只追加、不可改。

## 5. 六条设计底线（和"写个脚本直接传"的本质区别）

1. **文件先行**：身份还没对上号，文件也先安全收着——归集不被业务核对阻塞。
2. **绝不猜数据**：条码 0/1/N 分别处理、前导零不归一、患者与就诊分离、
   无确认就诊不选最新。宁可等待/转人工，不赌。
3. **冻结不可变**：报出去的包永远不改；更正 = 新版本。
4. **下载 ≠ 确认**：对方把文件拉走了，不等于医保业务成功——界面上分列展示，
   无回执不显示成功。
5. **幂等与断点**：同一个请求发十次，结果一样；断点续传只补缺。
6. **全程留痕**：每一步谁、何时、看了/改了什么，都有审计；Mock 环境显著标注，
   不会被误当真实平台。

## 6. 出了故障怎么办（可靠性，人话版）

| 故障 | 系统行为 |
|---|---|
| 工作站断网 | Agent 本地记账，网络恢复后从缺口继续，不丢不重 |
| 服务器中途崩溃 | 已收未登记的分片，重启时自动补账；合并到一半的，按"提交意图"恢复 |
| 上传会话超时/被取消 | 自动释放磁盘预留、清理暂存（不会占着茅房导致后续误报"磁盘不足"） |
| 对方接口超时不回包 | 标记"结果未知"，按原幂等键去查询恢复——**不新建重复业务** |
| 对方一直不回执 | 指数退避轮询，最多 60s 一次；界面始终显示"待确认" |
| Agent 本地队列文件损坏 | 保留故障副本供排查、换新队列继续；已传内容靠服务端幂等恢复，不重传 |
| 重复/乱序回执 | 以先到为准；旧回执不会把新版本状态改回去 |

以上每一条都有自动化测试断言（当前 81 项测试全部通过）。

## 7. 控制台页面导览（18 页，按用途分组）

**监控**：总览（KPI、状态分布）、质量队列（哪里卡住了、怎么修）、系统审计（谁干了什么）。
**日常业务**：病理工作台（病例全貌：版本树/索引/包/提交，分列状态）、关联复核
（歧义条码人工选择，理由必填）、设备采集（工作站状态、下发命令）、文件资产（校验/重校验）。
**配置（实施期）**：连接器（PIS/HIS 数据源）、字段映射、字段血缘（每个值从哪来）、
流程编排（上报工作流 DSL 校验）、医院配置包（字典/策略，审批后才生效）。
**上报**：发布与上报（PUSH 明细+回执证据）、视图发布（PULL 货架）、对账（差异快照）、
指标导入（CSV 表格类数据）。
**系统**：存储管理（卷/预留/余量）、外部阻断（B01—B09，还差什么外部条件）。

## 8. 现在能做到什么 / 还不能做什么（如实）

**已验证**（81 项自动测试 + 17+ 页浏览器实测 + 采集端 exe 端到端实测）：
本地全链路闭环（扫描→归集→关联→质检→冻结→双路上报→回执→对账）、
各类故障注入（断网/崩溃/损坏/重复）、性能基线（600MB 文件流式传输服务内存约 95MB、
万级待传队列）、Windows 工作站免安装 exe。

**还不能（等外部条件，见"外部阻断"页 B01—B09）**：连接真实 PIS/HIS 数据库（需授权）、
真机扫描仪（需厂商答复）、正式医保通道（协议未发布）。这些处于"现场待验证"，
**不得宣称生产接入完成**。

**生产前要补的工程项**：PostgreSQL 环境回归、清洁环境安装演练、50GB 大文件压测等
（清单在 `docs/实施状态矩阵.md`）。
