## 4. 计划部署拓扑与版本原则

### 4.1 Linux 目标首选形态

核实目标是受支持的 Linux x86_64、Docker/Compose 可用且院方允许容器后，采用单机 Compose。使用独立 Compose 项目名 `blyb`，不碰前置机上的既有项目。部署服务：

| 服务 | 职责 | 默认暴露边界 |
|---|---|---|
| nginx | 控制台、core API、storage 的同源入口 | 院内管理网 HTTPS 443；若端口占用先选独立端口并登记 |
| core | 配置、管理、认证、审计 | 容器内部 8000，不默认映射宿主机公网端口 |
| storage | 文件接收/校验接口 | 容器内部 8001，经 nginx 明确路径进入 |
| exchange | 已授权发布快照及下载能力 | 容器内部 8002；没有实际需求时不对外开放 |
| worker | 租约、工作流、抽取、回执与对账 | 无入站端口，首期恰好 1 个执行器 |
| db | PostgreSQL 核心元数据 | 内部 5432，不映射到全部网卡 |
| migrate/bootstrap | 编号迁移及受控初始化 | 一次性任务，不随 API 重启重复灌种子 |
| mock | 仅验收用模拟平台 | 独立验收 profile；正式运行默认不启动、不自动发送 |

保留交换 SQLite 的既有设计边界，核心迁往 PostgreSQL不等于必须把独立交换库同时重写。首期不新增 Redis、Kafka、Kubernetes、Celery 或新的分布式存储。扩多 Worker 必须单独证明副作用幂等及租约长任务安全，不能简单 scale。

院方允许目标出网时，上报适配器部署在目标，直接使用批准的 HTTPS 出口。院方只允许交换区出网时，把明确受控的出站组件放在交换区，通过持久任务交接和持久结果回传连接内部平台；这需要开发并验收，不假定当前已有跨机 Worker。**不因用户称“前置机”就自动把 root SSH 主机变成双网业务网关。**

### 4.2 非 Linux / 容器不可用分支

- 若目标为 Windows，使用已有 Windows 材料作为参考，但必须先完成分进程和服务托管，不能把 run_dev.py 多线程演示启动等同生产服务。
- 若 Linux 禁止 Docker，在独立 venv + systemd 下运行同样的单进程服务边界和 PostgreSQL；先发行构建再安装，不覆盖系统 Python。
- 选一个经过实测的分支并固化，不同时维护两套未验证发行路径。

### 4.3 版本与发行包

本机历史实测为 CPython 3.14；现有 Dockerfile 使用 3.12-slim，Linux 路径尚未验收。在隔离 Linux 构建环境选择与当前代码和依赖兼容的明确 Python patch 版本并锁定；优先验证现有 3.14 版本线，禁止静默换版本造成依赖不兼容。

PostgreSQL 初始候选沿用仓库 Compose 的 16 版本线，最终镜像固定 patch 标签与 digest。所有生产镜像、Python 依赖、前端依赖均写 manifest，禁止 latest 和宽松依赖作为最终发行依据。前置机 Python 3.9.9 仅可用于只读运维，不安装/替换其系统 Python。

Windows 的 cp314-win_amd64 wheelhouse 不能拿到 Linux 安装。现有 requirements.lock.txt 混有构建机其他库，不能直接作为 Linux 最小生产锁。需生成目标架构兼容的最小运行锁、独立测试锁和 Linux 发行材料；新增数据库驱动等依赖写明用途并锁版本。

以下来自当前代码阅读，是下一阶段工作项，不是已完成实现：

| 缺口 | 处理和验证要求 |
|---|---|

| get_app 是工厂，Compose 未显式 --factory | 用显式 factory 启动并验证实际可请求，不能仅依赖 Uvicorn 自动猜测 |

| 对象根和共享卷路径可能不一致 | core、storage、worker 使用同一对象根定义与一致目录；exchange 只读授权对象；验证 sentinel 与 UID/GID 权限 |
| 前端构建版默认 127.0.0.1:8000/8001 | 增量支持部署时同源默认；storage 使用 /storage 前缀并由 nginx剥离，旧手动地址仍可兼容；用另一台客户端浏览器验证 |
| Compose 无完整 restart / readiness /日志轮转 | 配置重启策略、数据库就绪、失败迁移禁止拉起、worker 心跳/积压指标、日志与磁盘控制 |
| exchange /health 仅返回 UP | 验收时同时检查真实数据库/卷/授权 API，不把单个 health 200 作为业务成功 |
| Dockerfile COPY packages 会带入运行数据库的风险 | 增加发行白名单和 .dockerignore，排除 var、SQLite、缓存、凭据、node_modules、测试数据；原始文件保留 |

seed 原有内容包含演示目的地和配置，不能未经核查就当生产初始化。利用已有 seed 的认证/卷逻辑实现最小幂等 bootstrap，避免复制整套业务初始化。首次初始化不批量读取患者资料，不创建对外自动发送任务。

## 6. 目录、资源与持久化

建议目标目录（实际依据 df/lsblk 选择可用挂载点，禁止格式化或重分区）：

```text
/opt/blyb/releases/<release-id>/     不可变发行目录
/opt/blyb/current                   当前发行引用
/etc/blyb/                         配置和受限密钥文件
/data/blyb/postgres/                PostgreSQL 持久数据
/data/blyb/exchange/                交换 SQLite 与 WAL
/data/blyb/objects/                 对象和分片，保留卷 sentinel
/data/blyb/backups/<timestamp>/     一致性备份、配置、manifest
/var/log/blyb/                     受控日志或容器日志索引
```

若 /data 不是数据盘，使用实际数据挂载点并更新统一配置。不能把后续被挂载覆盖的空目录误当持久对象卷。数据库、应用配置、日志、对象须在容器重建后仍可用；同一服务器上的备份不能替代院方异机备份。

16C/32G/1T 是待核实资源，不作容量承诺。初始采用单 worker；给 OS 和缓存保留内存，限制数据库与服务合计容器预算，测量之后再调。药品结构化数据与病理 WSI 要分别估算日增量和保留期，1T 不代表足够长期存储病理图像。配置磁盘可用空间与 inode、水位、备份失败、最老待处理任务的告警；预警阈值需结合院方保留策略落地。

密钥使用独立服务账户和最小可读权限文件；运行期不使用 SSH root 密码作业务密码。数据库 URI 必须正确处理特殊字符，日志屏蔽凭据；bootstrap/enroll/DB/API Secret 互不复用。

### P2：完成最小部署修订并做隔离验证

### P3：安装基础平台

只安装到已确认独立目录，保持前置机和其他业务服务不变。用专用非 root 应用用户或容器 UID 运行服务。只对管理网开放确认过的入口端口，数据库保持内部访问；TLS 使用院方证书/受信链，不关闭证书校验。

部署顺序：校验发行哈希→准备目录和权限→加载固定镜像→生成不回显的独立密钥→启动 PG→迁移→最小 bootstrap→core/storage/exchange→单 worker→nginx。任何迁移失败禁止跳到后续，不能删库重来。

Compose 仅在产生并验证了修订后的发行文件后执行，例如：

```sh
cd /opt/blyb/releases/<release-id>/implementation
docker compose --project-name blyb --env-file /etc/blyb/runtime.env -f deploy/compose/docker-compose.yml config --quiet
docker compose --project-name blyb --env-file /etc/blyb/runtime.env -f deploy/compose/docker-compose.yml up -d db
docker compose --project-name blyb --env-file /etc/blyb/runtime.env -f deploy/compose/docker-compose.yml run --rm migrate
# bootstrap 与服务清单依照实际生成并验收的发行文件，禁止照抄不存在的子命令。
```

不运行 `down -v`、`docker system prune`、`rm -rf` 或通配删除，不结束未知占用端口的进程。安装脚本需幂等：第二次执行不清库、不轮换未要求轮换的密钥、不覆盖已生效配置。

## 3. 增量抽取与完整单据

优先选择可靠的单调变更序列；如果只提供更新时间，采用复合游标 `(updated_at, source_bill_id)`、固定本轮上界、重叠回看和本地去重。时间戳不可靠且缺少重扫/账本时必须明确其漏数边界，不能承诺绝对不漏。

推荐步骤：

1. 按主单分页发现完成且变化的单据；先读取整张单的全部明细，不把 SQL 行分页边界当业务单据边界。
2. 在数据库一致性读中取得主单/明细快照；来源不能提供快照隔离时，读取前后比较 source_revision并检查齐套，变化则等待重取。
3. 任何一张主单都必须区分0条码、1条码、N条码；0条不能空列表“成功”。缺码或无法解释的重复码进入质量等待。
4. 在平台同一事务中提交来源快照、来源版本、幂等导入键、待执行任务与采集 checkpoint；事务失败不能先推进 checkpoint。
5. 源采集 checkpoint仅代表本地持久化完成，不代表远端已经接收。平台上传/确认各有独立状态。
6. 重启后重取相同来源版本不能重复生成提交；更正版本形成新快照，但已受理旧单据的更正需进入显式处理，不能默认重新发出。
7. 处理删除、作废、迟到明细、同刻多单和跨日业务；不只扫描创建时间，不使用 offset 翻页处理持续变化数据。

来源视图后面的查询索引和性能由 HIS 人员验证；使用只读最小授权账号、允许对象名单、参数绑定、查询超时、分页与速率上限。不向用户开放任意 SQL 执行能力。

## 5. 状态与异常

以下是**拟实现的逻辑状态**，开发时映射到现有 Submission/Job 状态模型；不要声称这些状态已全部存在。

```text
来源发现 → 持久快照 → 质量等待 / 待发送
待发送 → 发送中 → 待平台处理 / 明确拒绝 / 结果未知
待平台处理 → 全部确认 / 部分成功 / 处理失败 / 超时待核实
```

- `HTTP 200`、`response_success`与队列标识均不能单独判最终完成。
- 轮询使用 `alibaba.alihealth.drugtrace.top.yljg.query.billstatus`，正确分页、限流和延后查询。
- 文档 result_type=3 表示处理成功；sub_process_flag=51为全部成功，52为部分成功。只有核对该单全部结果才推进全部确认；未知/缺失状态保留待核实。
- 部分成功需要获取失败码明细并提供明确人工处置；指南存在个别yljg/lsyd引用混用，调用医疗机构方法须核对。
- 连接中断/响应丢失/发送超时：保留原bill_code和请求快照，先查询确认；无查询结论时进入待核实，不反复改编号上传。
- 认证失败/权限包缺失/服务过期/不支持码/非法业务类型不是无限自动重试；限流/临时网络故障按有上限的退避与抖动处理。
- 本地幂等键建议包含tenant、destination、source_system、来源业务事件及固定版本。配置revision必须随提交固定；不能重试过程中悄悄使用新规则。

统一封装任务调度、限流、审计、配置快照；平台专有签名和错误映射在适配器中；病理模块不导入药品业务表，不放松病理原有身份与齐套规则。
