## B. 逐条发现（独立署名，自有依据）

### B1.【证实·重要】计划§5四项代码缺口断言全部属实（已逐条命令验证）

- psycopg 未列于 `implementation/requirements.txt`（grep 无命中），而 compose 环境变量用
  `postgresql+psycopg://…`——Linux 首次迁移即会 ImportError。断言成立且是**阻滞性缺陷**。
- `implementation/Dockerfile` 第5行 `FROM python:3.12-slim`，本机实测 CPython 3.14.4；
  版本线差异真实（与实施状态矩阵"生产锁定版本待验证"一致）。
- compose 三服务 command 均为 `apps.*.app:get_app` 且全文无 `--factory`（uvicorn 会自动
  探测工厂函数，故属"加固项"而非"必错项"——我判**部分成立**：不修大概率能跑，显式化更稳）。
- compose 无 PYTHONPATH；`packages/`、`plugins/` 的导入依赖开发态 `_bootstrap` 的路径注入，
  容器内是否成立取决于 Dockerfile COPY 布局，未实测。列为缺口合理。

### B2.【证实】计划§2的协作登记描述与仓库协议一致

`python scripts/ai_session.py status` 实测返回多条登记（含历史 running 记录），协作协议真实
存在；计划要求下一 AI 先协调占用再动手，与根 AGENTS.md「范围重叠时先读取对方记录」一致。

### B3.【证实·正面】view-contract 的安全口径与仓库既有红线一致

「禁止为标记已上传去更新 HIS 业务表」「幂等键含 tenant+destination+来源事件+固定版本」
「配置 revision 随提交固定」「dry-run 零副作用」「HTTP 200≠业务确认」与 implementation
既有 Submission/回执/对账模型（`plugin_registry.h_deliver_push`/`_store_receipt`、
回执轮询退避）完全同构，药品域按此契约可作为新 destination/domain 插件落地，架构上可行。

### B4.【疑问·中】exchange「无实际需求不对外开放」与 PULL 目的地的取舍未明说

计划§4.1服务表把 exchange 定为"没有实际需求时不对外开放"，但既有双目的地之一
PULL_PUBLICATION（视图发布给采集器拉取）依赖 exchange 网关可达。若首期关闭 exchange，
等于首期只保留 PUSH（码上放心恰为 PUSH，不受影响）——技术上成立，但文档未写明
"关闭 exchange ⇒ PULL 目的地不可用"这一推论，交接时易被误读。建议补一句。

### B5.【疑问·小】验收编号 B01—B05 与既有外部阻断 B01—B09 重号

计划§8自己声明了"不替代"，但两套 B 编号并存（阻断清单 B01=PIS数据库授权；计划 B01=视图增量）
在同一批交接文档里流转，误读风险真实。建议计划侧加前缀（如 X-B01）。

### B6.【疑问·小】view-contract§2.1未说明"多院区/多药房与租户"的对应假设

视图给了 source_system+pharmacy_code，对账§6按"来源机构、药房"划区间；但未明示
"一家医院一个租户、多药房在租户内"的假设。若实际是多院区集团，租户切分会影响
幂等键与对账区间。属契约应写明的边界假设。

### B7.【补充·计划遗漏的既有配置事实】同源化后 CORS 允许列表

计划§5正确指出前端构建版默认绝对地址 127.0.0.1:8000/8001（与 `apps/admin_web/src/api.ts`
现状相符）并给出 nginx 同源 + /storage 前缀方案；但未提 storage 服务现有 CORS 允许列表
（`BLYB_ALLOWED_ORIGINS` 默认仅 127.0.0.1:8000/localhost:8000）。同源化后 CORS 不再触发，
但若运维仍保留分离地址访问，需同步该环境变量，建议计划补记。

### B8.【证实·正面】文档自洽与交叉引用一致

P5→view-contract.md、计划§12↔契约§7 官方入口链接一致、README 阅读顺序覆盖两者；
