# Runbook：备份与恢复

范围：核心库（`BLYB_DATABASE_URL` 指向的 SQLite/PG）、交换库（`BLYB_EXCHANGE_DB`）、
存储卷目录（如 `var/volume1`；内网形态为 `var/intranet/volume1`）、
Agent 本地队列（`var/agent-queue.sqlite3`，可选）。

自动化验证：`tests/fault/test_storage_protocol.py::test_E03_backup_restore`（同机恢复）
与 `tests/integration/test_w15_restore.py`（**新根恢复**，本 runbook 第三节与其逐步对齐）。

## 一、备份

1. **停写**：停止服务进程（`Ctrl+C` 结束 `run_dev.py`，或
   `powershell -File deploy\intranet\stop.ps1`——它读取 pid 文件结束进程并核对退出；
   不要用"再起一个进程"来停写）。无法停写时依赖 SQLite WAL 一致快照（第2步）。
2. 复制（SQLite 需连同 `-wal/-shm`；或用 sqlite3 backup API 取一致快照——
   `python -c "import sqlite3;s=sqlite3.connect('core.sqlite3');d=sqlite3.connect('<backup>');s.backup(d)"`）：
   ```bash
   cp <core.sqlite3>*        <backup>/
   cp var/exchange.sqlite3*  <backup>/
   robocopy var/volume1      <backup>/volume1 /E /XD staging assembling
   ```
   PostgreSQL：`pg_dump`；卷：快照/robocopy（排除 `staging/`、`assembling/` 暂存目录）。
3. 记录备份时 `schema_migrations` 最大 step，恢复后核对（应不小于备份时）。

## 二、同机恢复（原地）

1. 恢复库与卷文件到原路径；`BLYB_DATABASE_URL` 指向恢复库。
2. 补跑迁移：`python -m apps.migrate`（幂等可重复；**不要**指望"任意服务启动自动迁移"——
   服务进程自身不执行迁移，迁移入口是 run_dev 启动序或本命令）。
3. 一致性校验（E03 已自动化三步）：
   - 资产可读：抽查 `GET /api/v1/assets/{id}/content` 206/200；
   - 位置存在：`asset_location` 每个 AVAILABLE blob 均有可达文件；
   - 孤立检测：`objects/**` 中不在 `asset_location.physical_key` 的文件**列出登记**（处理前不删）。
4. 交换库恢复后按 `publication.manifest_ref.batch_id` 与交换库 `release_batch` 对账；
   缺行不重复发布（generation 幂等，`publish_batch` 二次执行 0 行生效）。

## 三、新根恢复（对齐 `tests/integration/test_w15_restore.py`）

恢复到**全新根目录**且旧库/旧卷不可访问时，仅改 `storage_volume.root_ref` 不够
（S13：每条 `asset_location.physical_key` 都是绝对路径），完整步骤：

1. **备份**（同第一节；SQLite 用 backup API 一致快照）：
   核心库 + 交换库 + 对象卷（排除 staging/assembling）。
2. **恢复到新根**：新目录下放回 core.sqlite3、exchange.sqlite3 与卷目录
   （如 `<newroot>/vol`）；`BLYB_DATABASE_URL` / `BLYB_EXCHANGE_DB` 指向新位置。
3. **写新根哨兵**：`VolumeHandle(volume_id, <newroot>/vol, ...).ensure_sentinel()`
   ——等价于在新根创建 `.blyb-vol-<volume_id>` 文件；缺失时写路径会被
   挂载丢失探测拒绝（VOLUME_OFFLINE）。
4. **重映射（事务内两处）**：
   - `storage_volume.root_ref` → 新根；
   - **每条** `asset_location.physical_key`：以旧根为前缀替换为新根
     （`os.path.join(new_vol, os.path.relpath(key, old_root))`）。
5. **使旧根不可访问**（验证恢复确实不依赖旧介质）：释放旧库连接后把旧根目录改名隔离。
6. **验证**：
   - 资产从新卷读取：`asset_content` 逐资产返回路径以新根开头，sha256 与冻结值一致，
     Blob AVAILABLE；
   - 交换一致性：`release_batch`/generation 与核心库 `publication.manifest_ref` 对账，
     路由仍可解析（SUPERSEDED 保留窗口语义不变）；
   - **孤儿对象只登记不删除**：新卷 `objects/**` 中不在 `asset_location.physical_key`
     的文件列入清单（`test_w15` 以 orphan.bin 断言"存在且被登记"）。
7. 恢复中断与重跑：步骤4的重映射是幂等覆盖；重复执行 no-op。

## 不变式

- 正式 blob 不可变：恢复只校验/登记，绝不回写内容。
- 提交/发布快照不可变：恢复后不重算历史，仅对账补偿。
- 源清理默认关闭：任何恢复失败不影响扫描电脑原件。

## Linux 容器形态（2026-10-16 修订；OPS-02/03/04）

<prod-host> 上的备份/恢复由 `implementation/deploy/linux/backup.sh|restore.sh` 执行（root；
脚本内部统一 compose 入口，**不依赖当前目录**）：

- `backup.sh [--with-objects] [--no-stop]`（OPS-04 修订版）：**先静止后快照**——
  先 `compose stop worker/core`（只停原本在运行的；记录原状态），排空
  `BLYB_BACKUP_DRAIN_SECONDS`（默认5s）后，在同一静止窗口内依次
  pg_dump → 交换库 sqlite backup API 快照 → `/etc/blyb` 配置（600）→（可选）对象卷打包；
  结束后恢复原运行服务。失败时 EXIT 兜底 trap 只恢复**原先在运行**的服务。
  `backup.json` 记录静止窗口起止、停/启服务与实际数据路径；`--no-stop` 为降级模式
  （仅 DB 内部一致，如实记录，且不允许与 `--with-objects` 同用）。
- `restore.sh <backup-dir> [--project P] [--data-root D] [--etc-root E] [--release R]
  [--validate-only] [--allow-production]`（OPS-02/03 修订版）：
  1. 只读校验先行：SHA256SUMS、归档成员安全（绝对路径/`..`/符号链接/硬链接一律拒绝）、
     备份 runtime.env 必需变量非空、镜像兼容提示；
  2. **默认隔离演练**：独立 compose 项目（默认 `blyb-restore-drill`）+ 独立数据根/配置根，
     nginx 演练端口默认改绑 `127.0.0.1:18443`，不与生产 443 冲突；
  3. 生产路径保护：目标与 `/etc/blyb`、当前 runtime.env 数据目录重叠即拒绝，除非
     显式 `--allow-production` 且 `BLYB_RESTORE_CONFIRM_PRODUCTION=YES`（双确认）；
  4. 目标目录必须为空（非空拒绝，不清空）；路径必须落在数据根内（realpath 包含检查，
     符号链接绕过失败）；`--validate-only` 只校验不写任何文件；
  5. 执行：配置落位（不触碰 `/etc`）→ 演练项目 down（残留）→ 交换库/对象卷落位 →
     空库起活 → pg_restore（统一 compose 入口）→ 全栈健康门禁 →
     `restore-manifest.json` 记录路径映射与镜像说明。
- 升级/回滚：`upgrade.sh <new-release>`（先自动 backup.sh）；`rollback.sh <old-id>` 只切
  发行目录与镜像 tag，**数据库不自动降级**——迁移不兼容时按本 runbook 用备份恢复，不反复横跳。

### 恢复演练步骤（独立项目/目录；绝不覆盖生产目录）

```bash
# 1) 校验备份与计划（不写任何文件）
./restore.sh <prod-path>/backups/<TS> --validate-only
# 2) 独立项目 + 独立数据根执行（生产 /etc/blyb 与 <prod-path> 数据目录不动）
./restore.sh <prod-path>/backups/<TS> --project drill-$(date +%m%d) \
    --data-root <prod-path>/restore-drills/$(date +%m%d)
# 3) 验证：用备份时刻管理员令牌登录 https://127.0.0.1:18443/ui/，
#    核对租户/连接器/提交/对象抽查；比对该次备份的 schema_migrations 最大 step。
# 4) 清理（保留数据确认后）：docker compose --project-name drill-xxxx down（不加 -v 数据保留）
```

自动化验证：`tests/integration/test_drug_trace_ops.py`（fake-docker 演练：任意 cwd、
穿越/链接/非空/重叠拒绝、静止窗口顺序与失败恢复、`--validate-only` 零写入）。
真实隔离 PG 恢复演练（含 pg_restore 兼容性）安排在维护窗口按上述步骤执行并留证据。

同一服务器上的备份不能替代院方异机备份；异机备份目的地/加密/保留期/RPO/RTO 由院方签定（EXT-11）。
