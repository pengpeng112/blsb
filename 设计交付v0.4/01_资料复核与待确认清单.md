## 2. PACS材料实际规定了什么

S01的“数据采集对接说明”表2要求结构化信息通过医院备份库或临时库的数据库视图提供；非结构化文件支持FTP、SFTP、HTTP、HTTPS、LOCAL及DICOM相关服务。表19明确C-STORE由医院/影像云PACS主动推送，采集器提供IP、端口、AE Title。因此不是所有协议都由同一方主动发起。

数据关联链包括：申请、检查、RIS/PACS关系、序列、图像、介质服务器、报告、报告快照/图文图像、结算及明细、项目字典、医生、预约。系统ID明确用于处理同一医院不同系统的标识碰撞。

表5.4列有 `GM=病理`；表5.3列有视频100、普通位图200、DICOM 300、其他400；非DICOM检查允许构造兼容序列。**这些说明旧采集模型有容纳病理及非DICOM元数据的结构，不足以证明采集器能读取、显示或验收具体厂商WSI。**

S02第1—2页要求上传原始影像、索引和数据集，当前通知业务重点为放射类检查并有历史补传时间段。该通知不能单独证明全国病理云当前采用完全相同规则，也不能将历史截止时间作为本系统默认调度条件。

## 3. 需要进入协议问题单的原文冲突

| ID | 原文位置与现象 | 对开发的处理 |
|---|---|---|
| P01 | 正文/表1为 `CHK_INFO`，两张关系图为 `CHECK_INFO` | 内部统一为examination；对外视图名放Profile，待平台确认，可在获准后提供别名 |
| P02 | 表1及图中 `APPLY_ITEM_DIC`，数据集正文为 `APPLY_ITEM_INFO` | 不擅自选唯一正确名称；发布模块允许别名映射 |
| P03 | V1.1记录删除报告指标信息，正文与图仍含 `RPT_INFO_DETAILS` | 首版原型保留可选模型，不默认作为必交视图 |
| P04 | `hospitalSetNo`在结算主表长度60，明细表长度36 | 内部保存完整值；禁止截断制造关联；平台确认长度后才发布 |
| P05 | 医生引用字段常为36，医生表 `docHosCode` 为60 | 内部不限制为36；超长在Profile校验阶段阻断 |
| P06 | 申请表 `fixhospitalCode`，结算表 `fixHospitalCode` | 输出字段按数据集保留大小写映射，不在公共模型复制两列 |
| P07 | `acquistionTime`、`bookDpetName`等疑似拼写问题 | 内部用规范命名，对外不得未经确认擅自改名 |
| P08 | `imagePath`称相对路径；HTTP(S)协议说明又说介质服务器非必填项可不传 | 必须确认URL放哪、是否完整URL、基址如何提供、是否支持鉴权与Range |
| P09 | 正文要求DICOM无损压缩，另列NON-DICOM及其他文件类型 | KFB等是否接受、是否必须DICOM WSI、什么压缩语法可用，列上线阻断项 |
| P10 | 表2列C-GET/C-MOVE/C-STORE，存储类型字典只有QR | 内部区分三种操作；外部storageType取值由平台Profile决定 |
| P11 | `setlId`中文解释为医保就诊ID，而常见系统可能用相似名称表示结算ID | 按来源语义逐字段确认；不能仅按英文同名自动映射 |
| P12 | 多张主表有lastChangeTime，图像、序列等子表缺少变更时间 | 与采集器约定父级变更触发重读、补充增量机制或全量核对；不能自行增加对方不读的字段后宣称已支持增量 |
| P13 | 图2仍画申请直接关联结算，V2正文改为由结算明细携带applyNum | 以经过平台确认的V2明细关系实施，不照旧图直接join |
| P14 | 缺少采集周期、分页方式、删除保留时间、回执API及错误码 | 只实现配置与模拟，不虚构平台回执；PUBLISHED不是CONFIRMED |
| P15 | 内部定义医生ID、患者ID、检查ID长度不同且部分关联表无机构/systemId | 对外以专用发布库/账号分域，必要时使用持久外部ID映射，防止跨系统关联串线 |

S01中证件、日期等占位值属于该文档具体字段规则：在兼容出口经确认后使用，内部保留NULL、来源缺失和质量标记。不得把18个0当成真实患者证件参与病理索引生成；不得从“1700-01-01”推算患者年龄。

## 4. 病理正式索引与草案差异

S04第一页写总长78位，证件类型2位、最多6位；S03规定证件类型3位，索引常见79位。S05又有多类别及更长号码字段。开发中以S03实现正式索引组成规则，S04/S05只作草案映射参考，互不覆盖。

S03示例八段长度为3、18、1、10、20、14、12、1，合计79，含7个连字符是86。数据库不可用CHAR(79)。8段各自存储，展示串与传输序列化分离；实际传输分隔符、异常证件、业务号特殊字符及多类别拆分方式仍需确认。

每次提交至少绑定三个版本：索引规则、数据集规则、通道协议。另绑定医院映射和流程发布版本。任何版本变更先回放、生成差异，再发布；不重写已完成提交。

## 5. 厂商对话的正确解读

已确认的是：院方希望自动读取图片以便存储和上传；迪英加技术人员回复目前没有通用开放接口，可针对需求开发。对话指定了协调、产品和技术对接人，但未提供技术资料。

尚未确认：具体机型、软件版本、输出格式、落盘目录、按患者还是检查分目录、扫描操作自动化程度、条码包含什么、文件完成信号、接口费用与交付时间、安装我方Agent的许可、SDK读图/导出/商用分发能力。

“自动获取扫描结果”与“自动控制扫描设备”分开立项。首版只要求扫描结束后的自动采集，不承诺自动装片、启动扫描、对焦或替代病理技师操作。群中询问是否手工扫描目前没有答复。

优先索取“完成任务清单＋稳定玻片/扫描ID＋文件获取能力”，而非只要一个返回图片路径的接口。需求书见06；不向群成员自动发送任何信息。
