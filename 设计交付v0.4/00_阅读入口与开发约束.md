# 医院数据归集与上报平台：开发设计交付包

版本：v0.4；日期：2026-09-30；状态：内部开发设计基线，外部接入契约待确认。

本版将原病理上传系统升级为“通用数据归集与上报平台”，病理是首个业务插件。自行开发Windows采集端、文件存储管理服务、业务服务、交换服务和可视化控制台。可以复用数据库、HTTP、操作系统存储和图像SDK等基础组件；不要求自行实现文件系统、数据库、TLS或DICOM协议底层。

v0.4依据用户提供的真实库复核报告补强；首院细化规则以09/10及07第9—12节为准。v0.3保留供追溯，不再作为并行开发基线。

## 本版关键决策

| ADR | 决策 | 原因 |
|---|---|---|
| ADR-01 | 通用内核＋病理业务插件＋目标平台Profile＋医院配置包 | 新业务不应将病理号、玻片等硬编码进传输和任务底层 |
| ADR-02 | 同时支持PUSH、PULL_PUBLICATION、HYBRID | PACS实际材料是视图供采集＋文件获取，也列有DICOM主动发送 |
| ADR-03 | 自研Edge Agent和Storage Service，首版文件系统后端 | 满足采集和存储自主可控；以后用后端插件扩展NAS/S3 |
| ADR-04 | 控制面和文件数据面分离 | 数百MB/多GB文件不能经过JSON任务队列或写入数据库大字段 |
| ADR-05 | 单院独立部署、模块化单体、独立后台进程 | 降低首期交付成本，同时保留以后拆分边界 |
| ADR-06 | 发布快照不可变、待采集与平台成功分开 | 对方读过视图或下载文件不等于医保业务确认 |
| ADR-07 | 可视化配置只操作声明式DSL，不执行任意脚本 | 配置可校验、可回放、可审计，插件代码通过发行包交付 |
| ADR-08 | 未确认的格式、接口、字段默认禁止生产启用 | 不能把“接口会差不多”写成虚构的正式病理接口 |

## 给实施AI的硬约束

- 先实现最小纵向闭环，再扩展协议；每阶段提交可运行程序、迁移脚本、自动化测试、离线安装说明和已知限制。
- 不把PACS协议直接命名为正式病理医保协议；分别命名 `jinan-imaging-v2-draft` 与 `pathology-internal-v1`，后者仅内部使用。
- 不把厂商承诺“可以定制开发”解释为API已经存在；Dir模式也必须先确认实际目录、格式和完成信号。
- 不默认迪英加输出KFB；将KFB、SVS等视为平台拟支持格式，设备Profile单独声明实际能力。
- 不补造患者身份、报告、检查类别、医生编码；外部规则要求的占位值只能在对应Profile出口产生，并明确来源。
- 不以HTTP 200、文件hash相同、视图可见或完整下载代替业务验收成功。
- 不以文件名或病理号作为全局主键，不以文件hash合并患者或玻片。
- 不用任意Python/JavaScript/SQL字符串充当“可视化规则”；SQL连接器仅允许受控只读查询模板。
- 不从浏览器直接连接HIS、数据库或扫描文件共享；所有操作走后端授权和审计。
- 不自动删除扫描原件；首版源文件清理默认关闭。
- 不将占位适配器返回成功；未实现能力返回 `CAPABILITY_UNSUPPORTED`，UI标记“未实现/待联调”。
- Schema和示例描述的是拟议内部协议；提供的OpenAPI仅覆盖关键内部接口草案，实施时须扩展成与代码一致的完整接口文档。

## 默认部署基线与仍有选择的部分

默认Windows 10/11 x64或医院支持的Windows工作站运行Python Agent服务；院内Linux x86_64运行Python业务/存储服务、PostgreSQL和Vue3/TypeScript管理台。Python具体小版本以厂商SDK兼容验证为准，建议先验证3.12环境，不以最新版本为目标。服务器操作系统、数据库具体版本/服务名与权限待确认；用户提供的核验报告已定位首院PIS为SQL Server、HIS为Oracle。通用接口不绑定品牌，首院适配器按10实施。

本轮交付为详细设计、资料提取及可解析契约草案，未开发生产系统、未连HIS/PIS、未处理真实扫描文件、未测试平台上传。不包含任何真实生产账号或接口密钥。
