# 首院连接器与数据质量实施契约

本章是v0.4新增的规范性设计，细化04/05，并以09区分实证、候选与未知。源字段来自用户提供的核验报告；示例为我方接口，不是厂家承诺。核心代码不得写死本院表名、地址、条码长度、病理号格式或HIS码值。

## 1. 连接配置与权限

首院PIS插件 `pis.pitaya.sqlserver`、HIS插件 `his.medrec.oracle`，以连接器SDK接入，禁止业务插件直接持有任意SQL执行权限。运行驱动通过医院许可及数据库版本实测后锁定；SQL Server和Oracle是两套方言及连接池，不能用SQLite通过即声称真实驱动可用。

HospitalPack中保存 source_system_code、identifier_namespace、driver_ref、secret_ref、database/service、schema、模板清单、字段映射、timeout、最大并发、每页上限、读取窗口、时区及批准证据。主机信息从受控部署配置注入；示例只用无效占位主机，不携带内网密码。PIS数据库候选PITAYA/QPIS，schema为dbo；HIS表候选MEDREC.PAT_MASTER_INDEX、MEDREC.PAT_VISIT。Oracle服务名及版本未确认。

对象名只能从安装/发布时的允许列表选取并按方言引用，查询值全部参数绑定，不能把网页提交的表名、WHERE片段或排序表达式直接拼SQL。只读账户、连接/语句超时、取消、结果行数上限、访问审计是每个驱动的共同契约。禁止默认NOLOCK，不以脏读换性能。生产建索引/视图须由DBA实施，应用只迁移自己的库。

## 2. 条码反查与临床关联

### 2.1 PISConnector能力

| 方法 | 输入 | 返回及条件 |
|---|---|---|
| get_slide_by_barcode | SourceScope、barcode_raw、可选已验证病例上下文 | SlideCandidate[]；0/1/N均合法，原始值保留 |
| get_case | SourceScope、case_source_key | 病理主表快照；PathologyID唯一性确认前不得无条件视为PK |
| list_slides | SourceScope、case_source_key、cursor | 实际玻片及状态原值；不以qpsl拆造玻片 |
| get_applications | case引用、ReqNoteID等 | ApplicationCandidate[]，关系来源与时间语义 |
| get_reports | case引用、cursor | 报告原始行及来源键；版本/作废语义单列 |
| poll_changes | stream、checkpoint、limit | 已定义能力覆盖范围的批次，不夸称全量CDC |
| reconcile_partition | stream、键区间、checkpoint | 有界分页快照和完整性标记 |

SourceScope包含tenant、source_system、已批准database/schema及命名空间版本。结果必须包括 source_object、source_key、observed_at、raw_digest、证据级别，附字段血缘；raw证据引用权限独立。

SlideCandidate至少包含slice.Id（报告称源PK，接入时核验类型/约束）、qptmh原值、PathologyID、lkh及原状态。不可将qptmh定义为我方全局unique。内部slide以来源稳定键关联UUID；若换库/迁移导致主键重置，必须显式变更namespace并做迁移映射。

只读查询模板示意（固定对象经批准后生成，问号为SQL Server驱动值参数；不得直接照搬连接生产）：

```sql
SELECT TOP (2) Id, qptmh, PathologyID, lkh, qpzt, zpzt, tmdyzt
FROM [PITAYA].[dbo].[Pitaya_Slice]
WHERE qptmh = ?
ORDER BY Id;
```

TOP(2)足以判定非唯一，不代表只展示两条就是完整候选列表。0条返回NOT_FOUND；2条标记AMBIGUOUS/truncated并走有界人工查询；1条仍要核验病例、申请、状态和来源作用域。参数类型绑定须匹配源列，避免隐式类型转换全表扫描；源列若实际为数值，原条码字符仍单独保留，归一化规则经批准才启用。

### 2.2 端到端关联顺序

1. Agent交barcode_raw、扫描ID/版本、文件bundle和完成证据；可以完全没有pathology_no。原始文件先安全归集。
2. 服务端依设备Profile确定PIS来源域；仅应用已批准的条码规范化，保留变换前后值。禁止去前导零、按长度猜病理号、按lkh分隔符猜病理号。
3. 反查0条→`WAITING_EXTERNAL`，原因`BARCODE_NOT_FOUND`；新PIS事件可唤醒，超时转人工。多条→`WAITING_HUMAN/SOURCE_AMBIGUOUS`；不得取第一条或最新条。
4. 单条通过来源键取得病例；若文件名中病理号提示与PIS不一致，生成`IDENTITY_CONFLICT`，保留文件，不绑定到猜测的患者。
5. 用PIS.PatientID查询患者主索引；检查患者命名空间和PIS/HIS身份冲突。HisID、InPatientID、OutPatientID须逐个确认语义，不可互相替代。
6. 用明确申请/就诊引用定位就诊。住院使用经确认的PATIENT_ID+VISIT_ID；无VISIT_ID时保留患者关联但就诊等待，禁止“最近一次住院”。门诊/慢特病暂无已证实查询链路，适配器返回能力缺失或缺依赖。
7. 分别关联标本、蜡块、玻片、报告；外键未确认则保留未关联节点及quality_issue，不编造层级。预期清单只有在状态/范围被批准后才能用于齐套。
8. 质量通过且依赖齐全后冻结包。原件落盘成功、玻片关联成功、临床就绪、目标业务确认四个状态分别展示。

### 2.3 HISConnector能力

`get_patient(patient_ref)`返回0/1/N候选；`get_encounter(patient_ref, encounter_ref, encounter_kind)`必须精确；`get_source_dictionary(namespace, revision)`可由受控字典文件提供。源码不能内置“01必然等于111”。HIS暂不可达时允许按批准策略保留PIS证据，但不得把网络失败等同于HIS无记录或自动启用回退。

## 3. 首院字段映射表

| 内部字段/对象 | 来源候选 | 处理/缺口 |
|---|---|---|
| case.pathology_no | Pitaya.PathologyID | 字符串；当前观察七位，长度规则配置化；源稳定键/跨年重用待核验 |
| application.external_id | Pitaya.ReqNoteID / 集成申请号 | 原值交叉校验，关系基数不能假设恒一对一 |
| patient.source_ref | Pitaya.PatientID → HIS.PAT_MASTER_INDEX | 源域批准后精确匹配，不靠姓名 |
| encounter.source_ref | HIS.PAT_VISIT复合键 | PIS到VISIT_ID桥接尚未证实；门诊另行适配 |
| slide.source_key/barcode | Pitaya_Slice.Id/qptmh | Id用于稳定来源身份，条码作为查找索引 |
| block/specimen | Pitaya_Material.lkh / Pitaya_Specimen.SpecimenID | 标本—块外键未确认，不用字符串拼关系 |
| report.gross/microscopic/diagnosis | Rysj/Gjsj/Zdyj、集成表病理诊断 | 按语义字段保存；空值及冲突策略有版本 |
| report.source_key/revision | 各报告表源键＋内容摘要 | 报告流水号等于病理号不能证明版本唯一，补充报告分开保存 |
| index.application_time | 原始申请时间；CreateTime仅候选 | PIS本地创建不等于临床开单，不自动替代异常申请日期 |
| index.encounter_kind | 经确认申请时病人类型 | 不凭InPatientID非空判住院，不覆盖慢特病语义 |
| index.category | 权威字段/批准规则 | '--'为空；FreezingID、分表只作证据，不默认普通病理 |
| index.report_org | 报告出具机构→医保码批准配置 | 未确认时等待；扫描单位可能不同 |
| microscope/report attachments | V_PIS_IMAGE / 图像报告URL | 与WSI不同资产role；URL不是文件本体/长期快照 |

对于URL附件，下载服务须走医院允许的host/port/path和认证策略，禁止任意URL抓取；成功下载并保存hash后的资产才可冻结。报告页面地址不能默认当PDF或WSI地址。

## 4. 身份决策规则

每个字段值采用 `value + source_ref + source_field + observed_at + effective_at(可空) + rule_revision + evidence_ref`。权威配置按字段、时间和机构确定，历史申请不能无条件用患者主索引今天的新身份覆盖。

| 场景 | 默认动作 |
|---|---|
| HIS字典有经批准映射，PIS同号或无号，其他关联无冲突 | 使用已批准类型及号码，记录来源和有效时点 |
| HIS/PIS非空号码或权威类型相冲突 | WAITING_HUMAN，候选不覆盖；选择必须有理由/证据 |
| ID_TYPE空/脏值，但PIS号码校验通过 | 仅产生“身份证候选”，仍WAITING_HUMAN；不直接赋111 |
| HIS号码缺失，PIS存在 | 依医院已批准的回退规则；没批准则等待，不因为缺失率高放行 |
| 所有号码缺失/无效 | WAITING，不用病理号、出生日期或零代替证件 |

可选自动回退必须明确源字段语义、患者精确绑定、适用证件与规则版本、有效期、无冲突条件及医院批准证据；默认关闭。格式校验只是其中一个条件。字典修订或人工纠正触发新候选/新包，已冻结或提交版本不被重写。

## 5. 质量规则与人工处理

规则引擎在IndexCodec之前执行语义质量；IndexCodec只接受已解析、有血缘、通过指定规则版本的数据，再做字段编码/格式校验。不得把数据库查询、人工猜测和格式拼接混成一个函数。

| 规则码 | 检查与范围 | 默认结果 |
|---|---|---|
| QF-DATE-FUTURE | 申请时间晚于服务端评估时间+批准容差 | 阻断该索引，人工复核 |
| QF-DATE-BEFORE-BIRTH | 出生日期可靠且语义同一患者，申请早于出生 | 阻断；出生未知不伪造生日 |
| QF-DATE-ORDER | 同一申请/报告版本：报告或审核早于相应业务前序 | 阻断；外院会诊原报告与本次申请不混比 |
| QF-TIME-SEMANTICS | 未确认申请字段含义/时区，或只有本地创建时间 | 等待字段确认 |
| QF-ID-TYPE / QF-ID-CONFLICT | 字典未映射/身份冲突 | 分别等待字典/人工 |
| QF-CATEGORY / QF-ORG / QF-STATUS | 类别、机构、临床状态未批准 | 仅阻断对应业务就绪/索引/目标 |
| QF-SOURCE-KEY / QF-ENCOUNTER | 来源主键冲突/就诊不唯一 | 隔离关联，不取第一条 |
| QF-COMPLETENESS | 预期玻片范围/完成条件未知或缺片 | 不判齐套 |

每次校验固定evaluated_at、原值、规则修订、时区和容差，保证回放可解释。容差是HospitalPack配置（例如测试可设300秒），不是免检未来数年的借口。日期无效不能自动替换为now或CreateTime。病例存储不被质量错误阻止。

UI必须有问题队列（按设备/病例/规则/等待时长筛选）、来源值并排展示（默认脱敏）、证据与规则链接、候选差异、批准字典/更正/重新获取/重评估操作。人工处理需要授权、理由、证据和If-Match；可写本平台的纠正层，不能修改HIS/PIS。人工不能绕过目标正式必填/格式要求。对已提交数据显示将生成的新版本和更正任务。

## 6. 增量、回填与删除

首院未证实通用更新字段，因此必须先实现可恢复分页盘点+内容摘要，而非只做CreateTime轮询。每类实体分别申明覆盖：新增、修改、逻辑删除、物理删除、字典变更。

1. 初始采集先经DBA批准范围、索引路径、时间/行数预算，再按稳定键seek分页；只有源键确认后才启用。原始行/摘要与checkpoint在我方库同事务提交。
2. 若确认可靠更新字段，增加 `(change_time, stable_key)` 和固定watermark的增量通道，重叠读取并去重；否则CreateTime通道只标记“新增发现”。ReceiveFromHis仅覆盖其已证明的消息类型。
3. 活跃病例窗口优先重读；历史分区滚动盘点。记录每个stream/partition的last_complete_scan、覆盖范围、失败页、内容变化和距上次覆盖时间。周期/限流由源库预算批准，不承诺未评估的全库实时扫描。
4. hash使用带版本的规范化序列化：固定字段、排序、null/空字符串区别、时间与Decimal规则；不能hash采集时间。摘要变化产生不可变source_record_revision，重复读取不新增业务修订。
5. 多表读取不是跨SQL Server/Oracle原子快照；保存各自采样时间。父子范围不稳定时重读/等待；没有可信完整性证据时不因某页缺行就判病例或玻片被删。
6. 只有覆盖完整、没有失败且删除语义确认的盘点才能产生“缺失候选”；生产自动墓碑优先使用权威删除/作废证据，或经批准的跨多轮确认策略。源掉线、权限变更、换库不产生全量删除。
7. 回放保留源修订和规则版本。迟到补片、报告变更、作废触发新包/目标更正；目标不支持则等待人工协议处理，不修改旧快照。

## 7. 增补内部模型与接口

04原有quality_issue/manual_decision/source_checkpoint等继续复用，增补字段与实体：

| 实体 | 新增要求 |
|---|---|
| source_capability_revision | 实体流、源键、对象清单、变更覆盖能力、审批/证据、字典与查询模板版本 |
| source_reconciliation_run/partition | 范围、起止游标、完成/失败标记、计数、覆盖截止、删除资格 |
| association_candidate | acquisition/source_ref、候选slide/case、匹配依据、候选状态、rule_revision；不能提前写confirmed关系 |
| source_field_evidence | 对象/字段、源修订引用、有效时点、提取/映射规则；敏感值由授权证据对象承载 |
| quality_issue | 增加blocking_scope、rule_revision、evaluated_at、resolved_by_decision；复评后留历史 |
| pathology_index_record | 固定来源修订、dictionary_revision集合、time/identity/category/org规则版本 |

设计接口均为我方内部新增，完整OpenAPI由实施时与代码同步：

- `POST /api/v1/pathology/barcode-resolutions`：输入acquisition_id和已批准source_scope_ref，原条码取不可变manifest；202返回operation_id，worker持久化候选；不接收任意SQL或任意生产连接地址。
- `GET /api/v1/pathology/acquisitions/{id}/association-candidates`：候选分页、匹配证据、歧义说明；敏感字段分权脱敏。
- `GET /api/v1/quality-issues`、`POST /api/v1/quality-issues/{id}/reevaluate`：筛选与固定版本重评估；人工修正统一用04的manual-decisions接口，不提供直接PATCH成功状态。
- `GET /api/v1/connectors/{id}/coverage`：每个stream覆盖范围、更新/删除能力、盘点滞后与未证实项。

这些POST遵守04的幂等、tenant授权、审计及乐观锁约定。各个WAITING原因通过reason_code表达，不能无限增加互相冲突的任务状态枚举。

## 8. 验收证据层级

本地合成夹具验证算法；隔离数据库验证真实SQL方言/驱动/事务；医院授权只读窗口验证对象、字段及性能；真机验证扫描；正式平台验证业务接收。五类结果分别记录，不用一个“测试通过”合并。具体验收用例与阶段门禁见07及契约目录新增JSON清单。
