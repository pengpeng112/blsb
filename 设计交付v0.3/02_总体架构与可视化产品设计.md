# 总体架构与可视化产品设计

## 1. 产品定位与范围

系统名称建议为“医院数据归集与上报平台”。面向病理、影像、检验、病案、运营指标等场景，实现可配置数据接入、治理、附件归集、规则校验、平台发布/推送、回执与对账。

通用化通过统一数据契约、任务引擎和连接器实现；病理的玻片、蜡块、重扫、报告、医保索引属于独立业务插件。禁止把所有业务都压成一张“患者＋文件”表，也不要求所有业务都有患者——运营汇总指标可能只有机构和统计周期。

首期必须交付病理纵向闭环，并用一个“CSV运营指标→HTTP模拟上报”的独立场景证明通用性。这样能验证新业务无需改Agent传输、存储、任务和回执核心。

## 2. 数据类型与协议能力矩阵

### 2.1 数据契约维度

| 数据类型 | 内部表示 | 首期能力 | 扩展方式 |
|---|---|---|---|
| 结构化记录 | Dataset记录＋JSON Schema＋主键/版本 | JSON、CSV、数据库视图 | 新Schema和连接器，必要时领域插件 |
| 主子表业务包 | DataPackage＋typed relations | 病理检查、玻片、报告、费用引用 | 契约定义父子关系、基数、齐套条件 |
| 半结构化报文 | 原始消息资产＋解析结果 | JSON；XML解析插件接口 | SOAP/XML、HL7等插件及字典 |
| 单个二进制文件 | Asset＋Blob | 任意文件的字节归集和下载 | 特定格式的解码另由FormatHandler提供 |
| 多文件目录/容器 | AssetBundle＋成员清单 | 保留文件角色、相对路径、hash | 厂商格式、OME-Zarr等 |
| PDF/普通图片 | 资产＋可选预览 | PDF/JPEG/PNG技术预览 | 不作为诊断级图像工作站 |
| WSI病理图像 | 原件资产＋可选元数据 | 原件归集；格式识别可缺失 | 厂商SDK、OpenSlide、转换器 |
| DICOM | 有效DICOM资产＋DICOM标识 | 首期协议接口预留 | 经验证的DICOM网关插件 |
| 音视频/波形 | 原件资产＋类型元数据 | 原样存取 | 转码、流式播放按业务另行交付 |

“支持文件传输”不等于“支持查看内容”，也不等于“目标医保平台接受”。能力列表要分别展示 `transport/read_metadata/preview/convert/target_acceptance`。

### 2.2 接入和出口分开配置

| 方向 | 协议/模式 | 实施级别 |
|---|---|---|
| 源接入 | 本地目录、只读共享目录 | 首期必须 |
| 源接入 | HTTPS事件推送/轮询 | 首期通用实现，厂商专有格式等资料后适配 |
| 源接入 | PostgreSQL/SQL Server/Oracle只读视图 | 通用接口＋首院实际数据库驱动；其余明确标未启用 |
| 源接入 | CSV/JSON人工导入 | 首期必须，导入预览和逐行错误 |
| 源接入 | SFTP目录、SOAP、HL7 v2、FHIR、消息队列、CDC | 后续按需插件；不是首期全部实现 |
| 出口 | HTTPS JSON推送＋轮询/回调回执 | 首期通用实现和Mock验收 |
| 出口 | 数据库视图发布＋HTTPS文件下载 | 首期必须，作为PACS类对接参考方式 |
| 出口 | 文件交换目录＋manifest＋回执文件 | 第二阶段通用扩展 |
| 出口 | SFTP/FTP | 适配历史系统，具体协议由接收方确认；FTP不做默认 |
| 出口 | DICOM C-STORE/C-GET/C-MOVE及DICOMweb | 独立插件，按平台要求实现和一致性测试 |
| 出口 | 消息队列、SOAP、专有签名/加密SDK | 后续按需插件 |

每个连接器有独立能力声明、配置Schema、UI表单Schema、健康检查、预览、增量游标、限流、错误映射。入站HTTP端点与出站HTTP客户端是不同适配器，不能仅写一个“HTTP开关”。

## 3. 逻辑层次

| 层 | 模块 | 不应承担的职责 |
|---|---|---|
| 控制面 | 用户/权限、租户、连接器配置、Schema、映射、流程发布、设备管理、告警 | 不传大文件内容，不直接执行业务SDK |
| 源数据接入 | SourceConnector、Inbox、原始报文保留、游标 | 不决定医保最终成功 |
| 文件数据面 | Agent、Transfer、Storage、Download Gateway | 不按患者姓名猜测关联，不生成病理业务规则 |
| 治理与领域 | DatasetValidator、Mapper、RelationResolver、DomainPlugin | 不写死目标平台URL和认证 |
| 运行内核 | Job、DAG、租约、Outbox、幂等、退避、人工等待 | 不内置病理号正则或PACS表名 |
| 交换层 | DestinationConnector、ProjectionPublisher、Receipt、Reconcile | 不修改冻结的源事实与历史提交 |
| 领域插件 | PathologyPlugin、未来Radiology/Lab/MetricPlugin | 不直接访问其他插件内部表 |
| 适配包 | 医院字段来源、字典、目标Profile、设备Profile | 不在配置中携带可执行任意代码 |

**四类可版本化扩展单位：** Connector负责协议；DomainPlugin负责业务语义；DestinationProfile负责目标数据集及交付规则；HospitalPack负责医院具体来源与映射。新增目标平台通常新增Profile及认证/回执适配，新医院通常新增Pack，新领域才新增DomainPlugin。

## 4. 物理部署与网络边界

首院推荐独立部署，下列为逻辑服务，可以按负载共机：

| 进程/服务 | 推荐位置 | 网络与权限 |
|---|---|---|
| edge-service | Windows扫描电脑 | 主动HTTPS连接院内存储/API；只读扫描目录；写本机队列/日志 |
| core-api / admin-web | 院内应用服务器 | 为管理台和Agent提供授权接口；不暴露给医保采集器 |
| workflow-worker / scheduler | 院内应用服务器 | 执行连接器/规则、任务领取、回执查询；持久任务由DB管理 |
| storage-service | 存储服务器 | 接收和流式下载；对应用只暴露asset_id，不提供任意路径访问 |
| format-worker | 独立受控进程 | 只访问任务授予的原件和暂存目录，限制CPU/内存/运行时长 |
| PostgreSQL core | 院内数据区 | 元数据、配置、任务、审计；业务文件不存数据库 |
| exchange-publisher / gateway | 经医院批准的交换区 | 仅发布已授权快照及资产；禁止透传到HIS/PIS |
| exchange-db | 交换区独立数据库或受控实例 | 专用只读视图账号，仅可查发布数据；不开放核心表 |

如果医保采集器部署在院内，可由其访问受控发布库和下载服务；若在另一网区，文件先复制到交换存储并完成校验再发布。不得为方便接入将HIS或扫描共享目录直接暴露跨区。

无需首期Kubernetes、Kafka或自建分布式存储。核心API、存储和Worker从同一仓库分进程运行；接口、数据所有权和状态约束明确后再拆服务。核心库与交换库分离，不依赖跨库分布式事务，按发布任务最终一致。

## 5. 通用数据包

DataPackage表示一个业务单元的不可变修订：`tenant_id、domain、package_id、revision、schema_ref、source_refs、records、relations、asset_refs、provenance`。某领域可无附件；某次文件归集也可先无患者，但正式业务提交必须满足领域规则。

公共信封只管来源、版本、关系、附件和追踪。病理payload由PathologySchema定义；指标payload由MetricSchema定义。不要把每个字段做成EAV行；业务实体关系和可索引字段关系化，扩展字段放有Schema约束的JSONB。

每条字段转换保留字段来源、规则版本和错误定位。去标识展示与真实交换值分离。原始值、规范值、目标值同时可追溯；UI默认展示脱敏值，查看原文需权限与审计。

## 6. 插件运行契约

插件发行清单包含 `plugin_id、version、api_version、capabilities、config_schema_ref、supported_os、dependencies、signature/digest、resource_limits`。

SourceConnector提供 `validate_config/test_connection/preview/poll/ack_checkpoint`；Publisher提供 `prepare/publish/revoke/query_evidence`；PushConnector提供 `validate/prepare_assets/submit/query/parse_receipt/reconcile`；DomainPlugin提供 `normalize/resolve/validate_completeness/build_package`；FormatHandler提供 `probe/extract/convert/verify`。

所有调用使用上下文：租户、trace、运行ID、配置快照ID、deadline、取消信号、授权资源。输出必须是结构化结果，不将异常字符串当成功结果。

配置注册不执行代码。Python插件随经过校验的发行包安装，厂商二进制在独立Worker执行；跨语言SDK可用本地受控RPC桥接。UI不能上传任意脚本或动态pip安装依赖。

## 7. 可视化控制台：页面与操作定义

### 7.1 导航与角色

主导航：总览、病理工作台、通用数据包、设备采集、文件资产、连接器、数据契约、字段映射、流程编排、目标平台、发布与上报、异常与对账、存储管理、配置发布、系统审计。

角色：平台管理员、实施配置员、业务复核员、运维人员、审计只读员、服务账号。权限按“功能＋租户＋来源/目标＋资产范围”组合，不以一个admin角色授权所有人。配置发布权限和病理身份改绑权限分别授予；是否双人审核由医院设置，首期至少完整审计。

### 7.2 页面详细行为

| 页面 | 主要内容 | 允许操作与反馈 |
|---|---|---|
| 总览 | 今日归集检查/玻片/文件/字节、缺失、积压时长、待复核、待回执、设备和磁盘 | 按时间、来源、目标筛选；统计卡可下钻；未知成功率不显示100% |
| 病理工作台 | 病理号、申请、脱敏患者、预期/有效/缺失玻片、报告版本、目标状态 | 检查详情显示玻片及扫描版本树、关联证据、质量与提交历史 |
| 关联复核 | 条码原值、文件名、PIS/HIS候选、冲突原因 | 选择明确目标、填写原因、查看影响范围；不能只输姓名强行绑定 |
| 设备采集 | 在线、最近盘点、监控目录、完成策略、待传数量/字节、带宽、版本 | 测试路径、模拟解析、暂停采集/传输、配置发布；不远程执行任意命令 |
| 文件资产 | 格式、大小、hash、所在卷、校验/副本状态、引用、下载记录 | 重校验、授权下载、迁移、查看原件/衍生关系；删除受引用与保留策略约束 |
| 连接器配置 | 来源/目标类型、端点、认证引用、游标、限流、能力 | 连通性测试仅探测；预览默认最多20行并脱敏；显示耗时/错误，不写生产数据 |
| 数据契约 | 字段类型/长度、必填条件、字典、主键、关系、版本差异 | 新建草稿、上传Schema、样本验证、发布；不可直接修改已发布版本 |
| 字段映射 | 左侧源字段，中间规则，右侧目标字段 | 拖拽或点选；条件映射、字典转换、日期/Decimal格式、数组展开；逐字段预览来源与失败 |
| 流程编排 | 有向节点画布、输入输出端口、条件分支、人工等待、重试策略 | 只连类型兼容端口；保存时检查环、孤立节点、未配置节点、必需依赖；执行前dry-run |
| 目标平台 | Profile版本、模式、范围、网络、认证、回执能力 | 启用前显示未确认项；PACS视图名/字段冲突必须选定已确认方案 |
| 发布与上报 | package/submission/publication、目标、版本、逐项状态 | 重试同一版本、更正生成新版本、撤回；分别标记待采集/下载过/平台确认 |
| 对账 | 应归集、实际归集、发布、远端回执差异 | 固定时间范围生成差异快照，勾选可恢复项提交补偿；不盲目全量重传 |
| 存储管理 | 卷容量/预留、暂存、正式、孤儿、损坏、副本、备份 | 新卷探测、迁移计划、清理预览、恢复演练结果；大操作显示影响清单 |
| 配置发布 | 草稿与当前差异、契约测试、影响设备、灰度批次 | 发布、回滚“未来执行所用配置”；明确不回滚已发生的外部发送 |
| 审计 | 操作者、动作、对象、前后版本、原因、时间、trace | 搜索/授权导出；界面没有修改/删除审计入口 |

### 7.3 一条检查的详情页

顶栏显示病理号、医院、登记来源及业务状态。下方分栏：来源证据、申请与就诊、标本/蜡块/玻片、文件与扫描版本、报告历史、质量问题、提交/发布、回执与审计。

每张玻片显示“预期有无、扫描版本、有效版本、文件集合完整性、是否被当前提交引用”。重扫版本不能自动覆盖原件；有效版本选取规则和人工动作均留痕。用户可直接定位“为什么这次未上报”，而非只看到FAILED。

### 7.4 可视化映射的约束

映射编辑器支持字段取值、常量、字典映射、空值回退、条件表达式、日期格式、Decimal变换、字符串连接和数组映射。表达式只调用白名单纯函数；不允许网络、文件、系统命令、数据库写入、任意eval。正则有长度和执行时间限制。

字典映射必须指定namespace和version；没有命中时默认阻断必填字段，不自动归“其他”。数组型字段在内部保留数组，目标要求逗号拼接时只在输出层处理，并校验元素顺序一致及分隔符转义。

SQL预览、URL测试、文件目录探测都由后端限制到预登记资源范围；可视化配置不是绕过网络与文件访问权限的入口。

### 7.5 产品交互验收

UI所有异步操作返回operation_id，显示排队/运行/成功/失败及可操作建议；支持取消尚未执行的任务。分页列表使用游标；大范围批量操作先预览数量和范围再提交。时间显示院内时区并可查看原始时间；文件大小统一单位并显示原始字节数。

首期流程画布可只提供固定节点类型和线性/条件分支，必须能保存、验证、发布、执行和回放；不能仅画出一个无法运行的拖拽页面。所有配置页面必须由后端Schema复验，不能只做前端必填校验。

## 8. 非功能需求和扩展验收

同一来源重复事件、同一任务重复执行、相同文件重复上传都应收敛到幂等结果；租户隔离贯穿API、后台任务、DB、文件下载和缓存。

使用流式I/O，进程内存不得随单个文件大小线性增长。建议首期测试50GB稀疏/合成文件和实际最大切片，测试至少1万待传文件及可恢复长队列；这些是工程验收负载，不宣称扫描仪实际支持50GB。

以单工作站起步，验证多工作站并发、优先级与实时/历史补传公平调度；实际吞吐SLO由测试环境测得，不在缺少硬件数据时承诺固定GB/s。首期建议设计目标为设备恢复连通后2分钟内重新开始可传任务，具体在部署验收中记录。

数据库轮询、文件归集、临床关联和医保出口分别设置并发及重试预算。网络故障不能把HIS连接池占满，历史补传不能无限挤占当天检查。
